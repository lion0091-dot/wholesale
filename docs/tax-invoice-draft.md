# 계산서(면세) 작성 도우미

## 배경
ROADMAP §7. 국세청 전자계산서/세금계산서 자동 발행은 ASP 연동·과세유형별 위임 등 스코프가 커서
(Post-MVP) 손대지 않고, 그 전 단계로 "홈택스 수동 입력을 돕는 초안 도우미"만 구현했다.
거래명세서(`docs/transaction-statement-pdf.md`)와 마찬가지로 국세청에 정식 발행되는 문서가 아니다.

## 과세/면세 판단 (잠긴 결정)
축산물 도소매는 절단·세절·냉동·포장 수준까지는 부가가치세법 시행령 제34조상 **면세**(미가공
식료품)로 인정된다. 가공육(햄·소시지·조미육 등)만 과세 대상이다. 현재 플랫폼 취급 품목은
면세 기준으로 판단해 **세액 없는 "계산서"** 양식으로 만들었다 — "세금계산서"(과세, 세액 10%
포함)가 아니다. 나중에 가공육 등 과세 품목을 취급하게 되면 별도로 세액 포함 양식을 추가해야
한다(지금 이 기능을 "과세"로 되돌리거나 세액을 끼워 넣는 수정은 하지 말 것 — 잘못하면 면세
품목에 세금계산서를 잘못 발행하는 세법 위반 서류를 도와주는 꼴이 된다).

## 아키텍처
- **데이터**: 별도 로더를 만들지 않고 거래명세서와 동일한 `lib/orders/statement.ts`의
  `loadStatementDataForSupplier` / `StatementData` / `findMissingStatementFields`를 그대로 재사용한다
  (필요한 필드 — 공급자/공급받는자 사업자정보, 품목, 합계금액 — 가 이미 다 있음).
- **PDF 렌더러**: `lib/pdf/tax-invoice.tsx` — `@react-pdf/renderer` 기반, 거래명세서와 같은 폰트
  등록 패턴(Noto Sans KR 정적 인스턴스) 재사용.
- **응답 생성**: `lib/pdf/tax-invoice-response.ts` — 거래명세서의 `statement-response.ts`와 동일한
  가드(공급자 주소 미등록 시 422 경고 HTML). `lib/pdf/statement-warning-page.ts`에 `documentLabel`
  옵션을 추가해 "거래명세서"/"계산서" 문구를 공유한다.
- **라우트**: `app/dashboard/orders/[id]/tax-invoice/route.ts` (GET, `runtime = "nodejs"` 필수).
- **초안 입력 폼**: `components/tax-invoice-draft-panel.tsx` — 작성연월일/업태·종목(공급자·공급받는자)/
  비고는 DB에 저장된 값이 없어(임의 기재사항) 이 화면에서 매번 입력받아 쿼리스트링으로 라우트에
  전달한다. 저장하지 않고 미리보기/내보내기 시점에만 반영(=값을 DB에 영속화하지 않음).

## 잠긴 설계 결정
- **면세 계산서만 지원**: 위 "과세/면세 판단" 참고. 세액 컬럼 자체가 없다.
- **업태/종목/비고/작성일자는 DB 컬럼을 만들지 않음**: 계산서 필요적 기재사항(등록번호·상호·
  성명·작성일자·공급가액)은 이미 있는 데이터로 충분하고, 임의적 기재사항(업태·종목·비고)까지
  스키마에 넣을 필요가 없다고 판단 — 매번 화면에서 입력받는 걸로 충분.
- **공급사(백오피스) 전용, 바이어 화면 없음**: 계산서는 공급자가 발행 주체이므로 작성 도우미도
  공급사 백오피스에만 붙였다. 거래명세서처럼 바이어용 라우트를 추가로 만들지 않았다 — 필요해지면
  그때 추가.
- **자동 발행 아님**: 이 PDF는 사람이 보고 홈택스 등에 직접 입력하는 참고용 초안이다. 국세청 API
  연동은 ROADMAP Post-MVP.

## 남은 과제
- 실계정 라이브 검증(공급사 로그인 → 계산서 작성 도우미 → PDF 확인) 안 함.
- 가공육 등 과세 품목 취급 시작 시 세액 포함 "세금계산서" 별도 양식 추가.
- (Post-MVP) 국세청 API 연동 자동 발행.
