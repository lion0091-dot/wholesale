# 재고 재설계 — "재고는 박스, 상품은 조건" (설계안, 2026-10-01, 승인 전)

사장님과 2026-10-01 논의로 확정된 전제 위에서 쓴 설계안이다. 코드는 아직 없다. 승인 후 로컬에서 끝까지 만들고 한 번에 전환한다.

## 0. 왜 바꾸나 (한 줄)

지금은 박스마다 상품 하나를 꽂아 넣는 구조라, 등급이 섞인 로트 박스가 **첫 번째 개체의 등급으로 "1+ 등심" 재고에 통째로 들어간다**(2026-10-01 실조회 `L02011163016114`: 22개체 = 1++ 5·1+ 2·1등급 15 → 현재 코드는 "1+"로 등록). 정밀한 척하는 거짓 재고다. 거래처 포장 관행은 바꿀 수 없으므로(원도매·중간도매 모두, 로트·개체번호 모두 받는다) 시스템이 "오는 대로" 받되 **아는 것과 모르는 것을 구분해 보여주는** 구조로 간다.

## 1. 확정된 전제 (사장님 결정)

| # | 전제 |
|---|---|
| 1 | **재고의 실체 = 우리가 찍은 박스 행**(`inbound_scans`). 이력번호는 꼬리표의 출처일 뿐 재고 단위가 아니다 (9/24 잠긴 결정 유지) |
| 2 | **꼬리표는 전부 조회로 채운다.** 개체번호 → 그 값 그대로. 로트 → 구성 개체를 순회해 **같으면 값, 다르면 "혼합"+구성표**. 대표값(첫 개체 값) 금지 |
| 3 | **상품 = 조건 집합**(축종·부위·원산지·등급·성별·BMS·냉장/냉동 중 정한 것만). 조건 1개짜리("등심")도, 6개짜리도 공존. 상품 재고 = 지금 조건에 맞는 박스 합 |
| 4 | **같은 박스가 여러 상품 재고에 동시에 센다.** "등심" 3박스 안에 "1++ 등심" 1박스가 들어 있는 식. 혼합 박스는 두루뭉술 상품에만 세고, 정밀 상품엔 "열어봐야 아는 것 N박스"로 따로 표시 |
| 5 | **재고 화면 = 축 순서로 접는 트리**(축종→부위→원산지→등급→성별→BMS→냉장/냉동). 분류표를 사람이 관리하지 않는다. 박스가 있는 조합만 나타난다 |
| 6 | **거래처에 요구하는 것 없음.** 발주서는 안 고친다. 입고 대조는 부위·중량으로 맞추고 등급은 참고 표시(혼합도 통과) |
| 7 | **현장 수작업은 실중량(+가끔 부위·보관위치)뿐.** "상품 지정" 단계는 없앤다. 유저가 로트·혼합·조건을 이해할 필요 없음 |
| 8 | 업체 유형(원도매/중간도매) 설정 없음 — 박스 번호 종류(개체/로트)로만 가른다. 같은 개체번호 박스 여러 개(부위별)는 정상 |
| 9 | **가공 단계(쪼개기) 포함**: 지육·대분할육 박스 1개 → 부위 박스 N개. 꼬리표 복사, 부모 소진, 수율 기록, 우리 라벨 출력 |
| 10 | 묶음번호 등록(소분 출고 신고)은 오프라인 그대로. 영업자 OpenAPI 가이드가 오면 별도 건 |

## 2. 데이터 모델

### 2-1. 박스 꼬리표 (`inbound_scans`에 열 추가)

| 열 | 뜻 | 출처 |
|---|---|---|
| `tag_species` | 축종(소/돼지/닭/오리/계란) | 번호 첫 자리·조회 |
| `tag_part` | 부위 | GTIN 학습 → 발주서 줄 → 사람 선택 (지금과 같음) |
| `tag_origin` | 원산지 | 조회(수입)·발주서·기본 "국내산" |
| `tag_grade` | 등급. 로트가 섞이면 `'혼합'` | 조회 |
| `tag_grade_mix` jsonb | 혼합 구성표 `{"1++":5,"1+":2,"1":15}` | 조회(로트 구성 순회) |
| `tag_sex` | 성별. 개체만. 로트는 null | 조회 |
| `tag_bms` | BMS. 개체만(1++만 옴). 로트가 전부 같으면 값, 아니면 null | 조회 |
| `tag_breed` | 품종(한우 등) | 조회 |
| `tag_storage_state` | 냉장/냉동 | 라벨·엑셀·사람(지금과 같음) |
| `slaughter_from`, `slaughter_to` | 도축일 범위(로트는 열흘씩 벌어진다) | 조회. 유통기한은 `slaughter_from` 기준 |
| `parent_scan_id` | 쪼개기로 생긴 박스의 부모 | 작업 화면 |
| `tag_source` jsonb | 각 꼬리표가 어디서 왔는지(`lookup`/`gtin`/`po`/`manual`/`inherited`) | 시스템 — 디버깅·"왜 이렇게 됐나" 설명용 |

- `master_livestock`(공용 이력 캐시)에 **구성 개체별 요약** 저장: `members jsonb` = `[{no, grade, bms, breed, slaughter}]`. `raw_payload`는 이미 있지만 매번 순회하지 않게 요약을 둔다. `grade`·`sex`·`bms` 대표값 열은 로트에서는 **더 이상 쓰지 않는다**(허위표시 원인).
- 허용값 목록(부위·등급·원산지)은 지금 발주서 품목 선택이 쓰는 목록을 그대로 쓴다. 새 분류표 없음.

### 2-2. 상품 = 조건 (`products` 재해석, 열 추가 없음)

- 지금 열 `category, subcategory(부위), origin, grade, breed, sex, bms, storage_state`를 **"조건, NULL = 상관없음"**으로 재해석한다. 열 추가 없이 뜻만 바뀐다.
- 정체성 유니크 인덱스(소 `idx_products_cattle_identity` 등)는 **조건 집합의 중복 방지**로 그대로 유효하다("등심 1++ 국내산" 상품 둘 금지). 다만 **NULL을 "상관없음"으로 쓰므로 `COALESCE(…,'')` 비교가 그대로 맞는다.**
- `products.stock_quantity`는 **캐시**로 남긴다 — 값은 "지금 조건에 맞는 박스의 남은 중량/수량 합"으로 `recalc_product_stock`이 다시 계산(아래 3-3). 화면·주문·핫딜·발주 추천은 지금처럼 이 열을 읽어 **코드 변경을 줄인다.**
- `inbound_scans.product_id`는 **"이 박스가 어느 상품 때문에 들어왔나"**(발주서 줄 연결·매입 단가 기준)로만 남고, **재고 집계에는 쓰지 않는다.** 없어도 된다(쪼개기로 생긴 박스는 null).

### 2-3. 혼합 박스의 정밀 재고 표시

- 정밀 상품 재고 두 숫자: **확실한 것**(조건 전부 만족) + **열어봐야 아는 것**(등급 조건만 `'혼합'` 박스에 걸리고 나머지는 만족). 후자는 `stock_quantity`에 **넣지 않는다**(주문 가능 수량은 확실한 것만). 화면에서만 "+혼합 3박스" 배지.
- 혼합 박스를 열어 1++만 꺼내 팔 때: 출고 스캔에서 중량과 함께 **꺼낸 등급**을 고른다(낱개 라벨에 개체번호가 있으면 찍기, 없으면 고르기 — 둘 다 지원). 그 출고분은 그 등급 판매로 기록되고 남은 중량은 계속 혼합.

### 2-4. 구체 예 — 로트 재고와 고객 노출의 매칭

입고(현장은 바코드+실중량만):

| 박스 | 번호 | 꼬리표(조회로 채움) | 중량 |
|---|---|---|---|
| A | 로트 `L02011163016114` | 등심·국내산·**등급 혼합**(1++5·1+2·1 15)·성별 모름 | 20kg |
| B | 개체 | 등심·국내산·1++·암·BMS 8 | 15kg |
| C | 개체 | 등심·국내산·1+·거세 | 18kg |

상품(조건+가격, 미니샵에 보이는 것):

| 상품 | 조건 | 고객에게 보이는 주문 가능량(`stock_quantity`) | 사무실 재고 화면 |
|---|---|---|---|
| 한우 등심 | 소·등심·국내산 | 53kg (A+B+C) | 53kg |
| 한우 등심 1++ | +등급 1++ | 15kg (B만) | 확실 15kg + 열어봐야 아는 것 1박스(A) |
| 한우 암소 등심 1++ | +성별 암 | 15kg (B) | 15kg |

고객은 로트·박스·혼합을 보지 않는다. 주문 배정: X가 "한우 등심" 10kg → 덜 특정된 A부터(정밀 박스 B를 아낌). Y가 "암소 등심 1++" 5kg → B. Z가 "등심 1++" 12kg → 확실한 10kg까지만(A 안의 1++는 열어보기 전엔 안 셈; 사무실이 A를 열어 출고 스캔에서 "A에서 1++ 4kg"으로 찍으면 그때 그 등급 판매로 기록). 거래명세서의 이력번호는 출고된 박스 번호(X는 로트, Y는 개체) — 지금과 같다.

## 3. 흐름

### 3-1. 입고 스캔 (현장)

1. 바코드 찍기 → 번호 종류 판정(개체/로트) → 조회 → **꼬리표 자동 채움**(2-1). 로트는 구성 순회로 등급 같으면 값·다르면 혼합.
2. 부위: GTIN 학습 → 그 거래처 열린 발주서 부위가 하나면 자동 → 아니면 드롭다운(지금과 같음).
3. 실중량 입력 → 등록. **끝.** "상품 지정" 단계·"확인 필요(상품 미확정)" 상태는 없어진다. 조회 실패(`EXCEPTION`)만 남는다.
4. 발주서 대조(`judge_scan_purchase_order`): **부위·중량**으로 줄을 맞춘다. 등급·성별·BMS는 **비교하지 않고 참고 표시**("발주 1++ / 입고 혼합"). 발주서에 없는 부위만 지금처럼 보류함.

### 3-2. 쪼개기 (작업 화면, 신규 `/dashboard/inbound/split`)

- 부모 박스 찍기(또는 목록에서 선택) → 줄마다 **부위 + 실중량** → "작업 끝".
- DB 함수 `split_inbound_scan(parent, lines[])` 한 트랜잭션: 자식 박스 N개 생성(`parent_scan_id`, 꼬리표 전부 복사, `trace_no` 동일, `scan_type='SPLIT'`), 부모 `remaining_weight` 0·상태 `SPLIT`, 원장에 `SPLIT_OUT`(부모)·`SPLIT_IN`(자식) 기록, 차이(뼈·손실)는 부모 쪽 `yield_loss`로. 끝에 `recalc_product_stock`(규칙: 재고 줄이는 함수는 recalc를 마지막에, 상품 행을 박스보다 먼저 잠그지 않는다).
- 자식 박스 라벨 출력: 기존 출고 바코드 생성(`bwip-js`)을 재사용해 **우리 바코드**(scan id)로. 이후 출고 스캔은 지금과 같다.
- 지육 발주서는 "소 1마리" 줄 하나(부위 없음) — 대조에서 부위 비교를 건너뛴다.

### 3-3. 재고 집계·출고 배정 (DB)

- `recalc_product_stock(product)` 재작성: `stock_quantity = Σ remaining_weight(또는 박스 수) of inbound_scans where 조건 전부 만족 and status in (NORMAL, …)`. 혼합 박스는 등급 조건이 있는 상품엔 제외.
- 박스가 바뀌면(입고·출고·취소·쪼개기·꼬리표 수정) **그 박스의 꼬리표에 맞는 상품 전부** recalc. 상품 수십·박스 수천 규모에서 인덱스 `(wholesaler_id, tag_species, tag_part, tag_grade)`로 충분 — 부하 테스트로 상한을 건다(기존 `perf-*.itest.ts` 방식).
- `apply_order_shipment` 자동 배정: 주문 상품의 조건에 맞는 박스 중 **① 기한 안 지난 것 ② 꼬리표가 적게 특정된 박스부터**(두루뭉술 주문이 정밀 박스를 먼저 소진하지 않게 — "등심" 주문은 성별 모름·혼합 박스부터) **③ 선입선출**. 잠금 순서는 "박스 → 상품" 유지.
- `stock_ledger`는 박스 단위(이미 `inbound_scan_id` 있음). `product_id`는 "그 변화가 어느 상품 주문 때문인가"로만.

### 3-4. 재고 화면 (`/dashboard/stock-ledger` 옆 새 탭 "재고 보기")

- 트리: 축종 → 부위 → 원산지 → 등급(혼합 포함) → 성별 → BMS → 냉장/냉동. 각 마디에 박스 수·중량. 기본은 부위까지 펼침.
- 모르는 값은 "모름" 가지(합계엔 포함, 아래엔 없음).
- 상품 카드 재고: "확실 N박스 M kg" + "열어봐야 아는 것 K박스".
- 순서 고정, 바꾸는 설정 없음. 위에 검색 한 줄.

## 4. 바뀌는 것 / 안 바뀌는 것

| 바뀜 | 안 바뀜 |
|---|---|
| 꼬리표 열 추가, 로트 구성 순회, 혼합 판정 | 바코드 파서, 조회 API 클라이언트의 호출부 |
| `recalc_product_stock`·`apply_order_shipment` 배정 규칙 | 주문·핫딜·결제·정산·거래명세서(전부 `products.stock_quantity`·`product_id` 그대로 읽음) |
| 입고 스캔의 "상품 지정" 제거, `PENDING_MAPPING` 상태 제거 | 발주서 구조·발주서 화면, 거래처 관리 |
| 대조 규칙(부위·중량만) | 보류함 흐름 |
| 재고 화면 신규, 쪼개기 화면 신규 | 출고 스캔 흐름(혼합 박스에서 등급 고르기만 추가) |
| 상품 등록 폼: "조건 선택" 설명(NULL = 상관없음), 성별·BMS 필수 해제 | 상품 정체성 유니크 인덱스 |

## 5. 전환 계획 (라이브 데이터)

1. **마이그 A**: 열 추가 + `master_livestock.members` + 함수 신설(옛 함수는 그대로). 라이브 적용해도 동작 변화 없음.
2. **백필**: 기존 박스의 꼬리표를 **지금 꽂힌 상품의 조건에서 복사**(상품에 있던 성별·BMS·등급이 박스로 내려감). 로트 박스는 `raw_payload` 순회로 다시 판정 — 섞여 있으면 `'혼합'`으로 바뀐다(이게 거짓 재고를 바로잡는 순간). 바뀌는 박스 목록을 먼저 뽑아 사장님께 보여주고 적용.
3. **그림자 비교**: 새 `recalc`를 옛 `stock_quantity`와 나란히 계산해 **차이 나는 상품 목록** 확인(혼합 로트 때문에 줄어드는 게 정상). 양방향 비교 테스트(검증 규칙).
4. **마이그 B**: 함수 교체(`recalc`·`apply_order_shipment`·`judge_scan_purchase_order`), 입고 화면 전환, 재고 화면·쪼개기 화면 배포. 같은 push.
5. 2주 뒤 옛 열·옛 상태값 정리(마이그 C).

## 6. 테스트

- 단위: 로트 구성 순회(같음/혼합/BMS 일부만/도축일 범위), 조건 매칭(NULL 상관없음·혼합 제외), 배정 정렬(덜 특정된 박스 먼저).
- 통합(로컬 DB): 입고 → 꼬리표 → 두 상품에 동시 집계 / 혼합 박스는 정밀 상품 제외 / 출고 배정이 정밀 박스를 아낌 / 쪼개기 트랜잭션(부모 소진·자식 N·원장·수율) / 발주 대조 등급 무시 / RLS(남의 박스 쪼개기 불가).
- 부하: 박스 5,000·상품 50에서 recalc·트리 조회 상한. 옛 느린 버전으로 되돌려 실패 확인.
- 따라가기: 입고·쪼개기·출고 카드 상태표를 `inbound-next-step.matrix.test.ts`에 추가.

## 7. 범위 밖 (이번에 안 함)

- 저울·라벨프린터 직접 연동(입력은 사람).
- 묶음번호 자동 발급·신고(영업자 OpenAPI 가이드 받은 뒤 별도).
- 사무실↔현장 교감(끝 신호·재확인 요청) — 보류 결정 유지.
- 핫딜·주문 UI는 손대지 않는다(`stock_quantity` 캐시로 호환).

## 8. 리스크·열린 질문

- **박스 안 낱개에 개체번호 라벨이 있는가** — 있으면 혼합 박스 출고 때 "찍기", 없으면 "고르기". 둘 다 만들어 두되 사진으로 확인.
- 소 외 축종(돼지 등급 1+/1/2, 닭·오리)은 같은 규칙 — 돼지 로트는 9/24 확인분으로 충분.
- 성별은 어떤 조회에도 로트에서 안 온다 → 로트 박스는 성별 항상 "모름". 성별 조건 상품 재고는 개체 박스·쪼개기 박스에서만 나온다(사실이므로 그대로 보여준다).
- 규모: 가장 큰 구조 변경. **승인 → 로컬 완성 → 백필 미리보기 → 한 번에 전환** 순서를 지킨다.
