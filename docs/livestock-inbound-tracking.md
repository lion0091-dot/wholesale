# 축산물 이력 입고 시스템 (바코드 스캔 + 박스 단위 재고)

### 배경
별도 스펙(축산물 도매업체용 SaaS — 입고 및 이력 검증)으로 들어온 요구. 창고 현장에서 바코드/카메라로 이력번호를 찍으면 축산물이력제 공공 API와 대조해 검증하고 입고를 자동화한다. 기존 `products.stock_quantity`는 **사람이 손으로 고치는 표시용 숫자**였고(`app/dashboard/products/actions.ts:289`가 유일한 갱신 경로), 주문이 확정돼도 차감되지 않았다 — 즉 재고 자동화가 아예 없던 상태에서 출발한다.

### 스택 결정 (2026-09-22)
원 스펙은 Node/Express(또는 NestJS) + Prisma/TypeORM 별도 백엔드를 전제했지만 **기존 Next.js + Supabase 위에 얹는 쪽을 채택**했다.

- 카카오 로그인/세션, `/staff-login`↔`/login` 분리, `middleware.ts` 가드를 그대로 재사용한다.
- 테넌트 식별자를 새로 만들지 않는다 — `wholesalers.id`가 곧 `company_id`다.
- **가장 큰 이유는 RLS**다. Prisma는 보통 service_role로 붙어 RLS를 우회하므로 테넌트 격리를 앱 코드가 매 쿼리마다 다시 책임져야 한다. 이 저장소는 RLS 정책 누락으로 이미 한 번 크게 데였다(`docs/wholesaler-retailers-rls-fix.md`).
- 대가: Supabase JS는 다중 문장 트랜잭션을 지원하지 않아 **입출고 핵심 로직이 TypeScript가 아니라 PL/pgSQL(RPC)로 간다**. 이 저장소가 이미 20곳 넘게 쓰는 패턴이라(`apply_credit_order`, `complete_supplier_signup` 등) 새로운 방식은 아니다.

### 잠긴 설계 결정

**1. 재고의 실제 단위는 이력번호가 아니라 "박스 한 개"(`inbound_scans.id`)다.**
이력번호는 고기의 신원이지 우리 창고의 물건 한 개가 아니다. 소 한 마리(개체번호 12자리)에서 등심 박스가 여럿 나오고, 묶음번호(15자리)는 애초에 여러 마리를 묶은 번호다. 그래서 `trace_no`에 UNIQUE를 걸 수 없고, 중복 스캔을 이력번호로 막을 수도 없다.

**2. 수량은 `stock_ledger`(원장)에만 쓰고 `products.stock_quantity`는 그 합계로 파생시킨다.**
취소는 행 삭제가 아니라 반대 부호 행 추가(역분개)다. `products`의 `CHECK (stock_quantity >= 0)`가 "이미 팔려나간 입고를 취소"하는 불가능한 상태를 막는 가드로 동작한다. 동시 스캔에서 lost update가 나지 않도록 read-modify-write 대신 `SUM(qty_delta)` 재계산을 쓴다.

**3. `products` 스키마는 변경하지 않는다.**
부위는 `products.subcategory`(20260930000022에서 이미 추가됨, 소: 안심·등심·채끝…, 돼지: 삼겹살·목살…), 축종은 `products.category`로 이미 있다. `stock_quantity`는 컬럼을 그대로 두고 **"누가 쓰느냐"만** 원장으로 바꾼다 — 8개 파일이 이 컬럼을 읽고 있어(`shop-view.tsx`, `product-table.tsx`, `catalog-types.ts`, `products/page.tsx` 등) 컬럼을 없애면 전부 고쳐야 하고 얻는 게 없다. **미니샵·발주 화면은 코드 변경 없이 그대로 돈다.**

**4. 이력번호 → 상품 매핑은 "부위 우선 + 못 채우면 되묻고 학습"이다.**
`master_livestock.part_name`으로 `trace_product_map`을 조회해 자동 매핑하고, 못 찾으면 `PENDING_MAPPING`으로 남겨 사용자에게 한 번 묻는다. 답하면 `trace_product_map`에 저장돼 다음부터 안 묻는다. 등급까지 일치하는 매핑을 등급 무관(`grade IS NULL`) 매핑보다 우선한다.

**5. 출고는 박스 단위로 추적한다.**
수량만 차감하면 "어느 거래처에 어느 소를 팔았는지"를 영영 알 수 없고, 나중에 붙여도 이미 나간 주문은 소급이 안 된다. `stock_ledger.inbound_scan_id`가 그 연결고리다. 목적은 두 가지 — 축산물 이력법상 거래내역 기록·보관(정확한 의무 범위·보관기간은 **시행규칙 확인 필요**, 아직 확인 안 함)과, 이미 있는 거래명세서 PDF(`docs/transaction-statement-pdf.md`)에 이력번호를 찍어 식당에 증명서를 자동 제공하는 것. **소매(식당) 화면은 두 방식이 완전히 동일하다** — 박스는 식당에 노출되지 않는다.

**6. 모든 쓰기는 SECURITY DEFINER RPC를 통한다.**
재고 관련 테이블에는 SELECT 정책과 SELECT GRANT만 준다. 원장을 우회해 재고를 직접 고치는 경로가 존재하지 않는다. 예외는 엑셀 업로드 큐(`inbound_import_jobs/rows`) — 재고에 직접 영향을 주지 않는 적재 단계라 수백 행을 RPC로 한 건씩 넣는 낭비를 피해 RLS 정책으로 직접 쓰기를 허용한다.

**7. 마스터는 미리 채울 수 없다 — 스캔 시점 Lazy Loading 캐시다.**
축산물이력제 API는 전체 덤프를 주지 않는다(이력번호를 알아야 조회 가능). 그래서 "플랫폼이 매일 마스터를 일괄 적재"하는 구조는 성립하지 않는다. 처음 들어온 이력번호는 반드시 한 번 API를 타고, 그 다음부터 캐시 히트다.

**8. Vercel Hobby라 크론 기반 큐 소화를 쓸 수 없다.**
`vercel.json`의 크론 슬롯 2개가 이미 소진됐고 Hobby는 하루 1회가 최대 빈도다(`app/api/cron/market-price-sync/route.ts:12` 주석에 같은 제약이 기록돼 있다). 엑셀 대량 업로드는 **브라우저가 `processChunk`를 반복 호출해 20건씩 소화하는 클라이언트 주도 방식**으로 간다 — 각 요청이 짧아 실행시간 제한을 안 건드리고, 진행률이 보이며, 창을 닫아도 job이 DB에 남아 이어서 처리된다.
> 참고: Vercel Hobby는 약관상 비상업적 용도 전용이다. 구독 과금(`docs/platform-subscription-billing.md`)을 실제로 시작하는 시점에는 Pro로 올려야 한다 — 이 입고 시스템 때문이 아니라 기존 과금 기능 때문이다.

**9. 출고 차감 시점은 '출고(shipping)'가 아니라 '확정(confirmed)'이다.**
출고 시점에 빼면 확정~출고 사이에 다른 거래처가 같은 물건을 주문해 이중 판매가 난다. 공급사가 "드리겠습니다"라고 확정한 순간 물건을 잡아야 한다. 재고가 모자라면 확정 자체를 막는다(`INSUFFICIENT_STOCK`) — "상태만 바뀌고 재고는 음수"보다 낫고, PG 환불 실패 시 취소를 막는 기존 정책(`docs/pg-payment-integration.md`)과 같은 방향이다.

**10. 출고 차감은 Server Action이 아니라 `orders` 테이블 트리거로 건다.**
상태를 바꾸는 경로가 대시보드 액션 하나가 아니다 — 운송장 등록 시 자동 출고 전환(`app/dashboard/orders/actions.ts`의 `shouldAutoShip`), PG 취소, 관리자 직접 수정이 모두 `orders.status`를 건드린다. 트리거면 어느 경로로 들어와도 재고가 따라간다. 외상 잔액 원복을 트리거로 처리한 `20260927000000`과 같은 판단이다.

**11. 원장에 처음 편입되는 상품은 기존 수동 재고를 `OPENING_BALANCE` 행으로 먼저 옮긴다.**
이게 없으면 첫 입고 스캔 순간 `recalc_product_stock()`이 재고를 원장 합계(=방금 찍은 박스 한 개)로 덮어써서 **기존 수동 재고가 통째로 증발한다.** 상품당 1행만 허용(멱등 인덱스). 이 덕분에 스캔을 전혀 쓰지 않는 상품도 주문 확정 시 자동으로 원장에 편입돼 출고 차감이 동작한다 — 박스가 없는 분량은 `inbound_scan_id IS NULL` 행으로 빠진다.

### 아키텍처

```
바코드/카메라 스캔
   │
   ├─ master_livestock 조회 (캐시 히트 → 즉시)
   │
   ├─ 미스 → 공공 API 호출 → upsert_master_livestock()
   │
   └─ record_inbound_scan()  ← 한 트랜잭션
         ├ 이력 못 찾음        → EXCEPTION       + exception_log
         ├ 이력 O, 상품 미확정 → PENDING_MAPPING + exception_log  → 사용자에게 되묻기
         └ 이력 O, 상품 확정   → NORMAL + stock_ledger(+) + 재고 재계산
```

```
주문 상태 변경 (어느 경로로든)
   │
   └─ trg_orders_stock_sync (AFTER UPDATE OF status)
         ├ → confirmed  : apply_order_shipment()
         │                  ├ ensure_opening_balance()  기존 수동 재고 이관
         │                  ├ 선입선출로 박스에서 차감 → ledger(-) + inbound_scan_id
         │                  ├ 박스로 못 채운 분량은 박스 없이 차감
         │                  └ 재고 부족이면 RAISE → 확정 자체가 롤백
         └ → cancelled  : reverse_order_shipment()
                            └ 나갔던 박스에 그대로 원복 + ledger(+)
```

### 테이블 (`supabase/migrations/20260930000053_livestock_inbound_core.sql`)

| 테이블 | 역할 |
|---|---|
| `master_livestock` | 공공 API 응답 캐시. 플랫폼 공용(업체 구분 없음), `raw_payload jsonb`에 원본 전문 보관 |
| `trace_product_map` | 축종+부위+등급 → 우리 상품 매핑 학습 (업체별) |
| `inbound_scans` | **박스 한 개 = 한 행.** 재고의 실제 단위. `remaining_weight`로 선입선출 출고 |
| `stock_ledger` | 입출고 원장. 재고의 유일한 진실. 멱등 유니크 인덱스로 재시도 중복 차단 |
| `livestock_exception_log` | 검증 실패 건(`NOT_FOUND`/`API_ERROR`/`INVALID_FORMAT`/`UNMAPPED_PRODUCT`) |
| `inbound_import_jobs` / `_rows` | 엑셀 업로드 청크 큐 |

### RPC

| 함수 | 역할 |
|---|---|
| `resolve_current_wholesaler_id()` | owner와 초대 직원 계정 모두에서 `wholesaler_id`를 얻는다. `get_current_wholesaler_id()`는 owner만 인식한다(20260930000024 참고) |
| `upsert_master_livestock(...)` | API 응답 적재. 공급사 계정만 호출 가능(공용 캐시 오염 방지). 재조회가 부분 응답이어도 기존 값을 지우지 않는다 |
| `record_inbound_scan(...)` | 스캔 + 원장 + 재고 + 예외를 한 트랜잭션으로 |
| `resolve_inbound_mapping(...)` | 미확정 건에 상품 지정 → 재고 확정 + 매핑 학습 |
| `void_inbound_scan(...)` | 역분개. 일부라도 출고된 박스는 `PARTIALLY_SHIPPED`로 차단 |
| `recalc_product_stock(...)` | 내부 전용(`REVOKE EXECUTE FROM PUBLIC`). 원장 합계로 `stock_quantity` 재계산 |
| `ensure_opening_balance(...)` | 내부 전용. 원장 첫 편입 시 기존 수동 재고를 `OPENING_BALANCE`로 이관 (설계 결정 11번) |
| `apply_order_shipment(...)` | 주문 확정 시 선입선출 차감. 이미 차감된 주문이면 무시(멱등) |
| `reverse_order_shipment(...)` | 주문 취소 시 나갔던 박스에 원복 |
| `sync_order_stock()` | `orders.status` 변경 트리거 본체 |
| `get_order_trace_numbers(...)` | 거래명세서/주문 상세용 — 이 주문에 나간 이력번호+등급+도축일 |
| `adjust_product_stock(...)` | 상품관리 화면의 재고 조정. 사유(실사/폐기/파손·손실/반품/기타) 필수, 차이분만 원장 행으로 남긴다 |
| `get_product_stock_boxes(...)` | 상품별 잔여 박스 목록 — 재고가 어느 고기로 채워져 있는지 |

### 상품관리 화면 변경 (3단계)
`products.stock_quantity`를 직접 UPDATE하던 "재고 수정"(`updateProductStockAction`)을 **재고 조정**으로 바꿨다. 직접 덮어쓰면 다음 입고/출고 때 `recalc_product_stock()`이 원장 합계로 되돌려 조용히 사라진다. 이제 차이분이 원장 행으로 남고 사유가 함께 기록된다. 폐기·파손으로 줄어든 건 `LOSS`로 구분해 나중에 손실률 집계에 쓸 수 있다.

### 상품관리 화면: 신선도 표시 + 경락가 패널 (4단계)
- **상품 목록에 도축일/포장일을 집계해 보여준다.** 상품 하나는 박스 여러 개로 채워져 있어 도축일이 하나가 아니다. **가장 오래된 박스 기준**으로 보여준다 — 선입선출 관리에서 실제로 봐야 하는 값이 "가장 오래 묵은 재고가 며칠 됐나"이기 때문이다. 14일/30일에서 색이 바뀐다. 스캔 이력이 없는 상품은 빈칸 대신 "이력 미등록" 안내를 띄운다.
- 목록에서 상품마다 따로 조회하면 N+1이라 `get_product_stock_summary()`로 상품별 1행씩 한 번에 집계해 받는다. 박스별 상세는 `get_product_stock_boxes()`.
- `master_livestock.packing_date`(포장처리일자)를 추가했다. 20260930000053에서 빠져 있었고, 인증키 미발급이라 실응답에 오는지는 미확인 — 안 오면 NULL로 남을 뿐이다.
- **상품관리에는 상품 줄마다 그 등급의 공공가를 붙인다.** 내 판매가 밑에 "공공 26,980원/kg"이 나란히 나온다. 매칭 키는 `products.category`(축종) + `products.grade`(등급)이고, 시세가 없는 축종(닭·오리, 양, 가공육)이나 등급 미입력이면 아무것도 표시하지 않는다. 상품마다 조회하면 N+1이라 화면을 열 때 최신 스냅샷을 한 번만 읽어 맵으로 만든다(`lib/market-price/product-match.ts`).
- **축종별 전 등급 시세는 별도 메뉴(`/dashboard/market-prices`)로 뺐다.** 내가 취급하지 않는 품목까지 보는 화면이라 상품관리와 성격이 다르다. 어드민이 아니라 **공급사 메뉴**에 둔 이유는, 어드민은 플랫폼 운영자 전용이라 정작 도매업체가 못 들어가기 때문이다(잠긴 결정).
- **판매가가 0원인 상품은 고객에게 노출하지 않는다.** 기존에는 `is_active`만 봐서, 값을 아직 안 매긴 상품이 미니샵에 "0원"으로 떠 주문이 들어올 수 있었다. RLS의 고객 분기에 `base_price > 0`을 넣고(`20260930000058`), `lib/shop/catalog.ts`에서도 한 번 더 거른다 — 공급사가 자기 미니샵을 열어보면 RLS의 "소유자" 분기를 타서 통과하기 때문이다. 공급사 목록에는 그대로 보이되 **"판매가 미설정 · 고객 비노출"** 배지를 띄운다.
- **경락가 열람을 공급사와 관리자로 좁혔다.** 기존 정책은 로그인 사용자 전원에게 열려 있어 카카오로 로그인한 바이어(식당)도 조회할 수 있었다. 공공 시세는 공급사 판단용이라 고객에게 노출되면 안 된다 — 미니샵에 위젯을 두지 않는 것만으로는 부족해서 DB 권한까지 막았다.

### 상품 등록/수정 폼의 재고 필드 (4단계에 포함)
`updateProductAction`이 `stock_quantity`를 직접 UPDATE하고 있었다. 목록의 "재고 수정"만 고치고 이 경로를 놓쳤으면, 상품 정보를 고칠 때마다 폼에 실려 있던 값이 재고를 덮어써 다음 입고/출고에 사라졌을 것이다.

- **수정 시**: `stock_quantity`를 UPDATE 대상에서 제외하고, 폼의 입력칸도 읽기전용으로 바꿨다. 변경은 목록의 "재고 조정"(사유가 원장에 남는 경로)에서만 한다.
- **신규 등록 시**: 최초 재고는 그대로 받는다. 원장은 아직 비어 있고, 첫 입고나 첫 주문 때 `ensure_opening_balance()`가 그 값을 기초재고로 옮긴다.
- **맞춤가격(`custom_prices`)은 손댈 게 없다.** 가격만 다루고 재고·원장과 무관하다(코드로 확인).

### 중복 스캔 경고 (5단계)
이력번호는 소 한 마리에 하나다. 그 소에서 나온 등심 박스가 3개면 **셋 다 같은 번호, 같은 바코드**다. 즉 같은 바코드를 여러 번 찍는 게 정상이라, `trace_no`만으로는 실수로 두 번 찍은 것과 진짜 다른 박스를 구별할 수 없다.

구별 단서는 **중량**이다. 박스마다 실중량이 미세하게 다르다(8.20 / 8.35). "같은 번호 + 같은 중량 + 10분 이내"를 의심 신호로 삼아 `DUPLICATE_SUSPECTED`를 던지고, 작업자가 "다른 박스가 맞다"고 확인하면(`p_confirm_duplicate = true`) 진행한다.

**자동 차단하지 않는 이유:** 실제로 같은 소에서 같은 중량 박스가 연달아 나올 수 있다. 막으면 정상 입고를 막게 된다.

**판정 대상은 `NORMAL` 스캔뿐이다.** 검증 실패(`EXCEPTION`)나 매핑 대기(`PENDING_MAPPING`) 건을 다시 찍는 건 중복이 아니라 재시도이고, 취소(`VOIDED`)된 건은 이미 재고에서 빠졌다. 중복이 문제가 되는 경우는 재고가 부풀 때뿐이다. **엑셀 일괄 업로드는 검사에서 제외한다** — 한 파일에 같은 규격이 여러 줄 있는 게 정상이고, 행마다 확인창을 띄울 수도 없다.

### 검증 상태 (2026-09-22)
로컬 Postgres 16에 **전체 마이그레이션 체인을 처음부터 적용**하고(Supabase `auth`/`storage` 스키마는 스텁) 기능 테스트 9종을 돌려 전부 통과:

8. 테넌트 격리 — B사가 A사 입고/원장 0건, 공용 마스터는 2건 조회

### 남은 과제
1. **공공 API 커넥터** (`lib/livestock/mtrace-client.ts`) — 인증키 발급 후 실응답으로 파싱 검증 필요. 특히 **부위(`part_name`)가 응답에 오는지**가 매핑 자동화율을 좌우한다. 이력번호가 개체 단위라 안 올 가능성이 있고, 그 경우 되묻는 빈도가 높아진다. 냉장/냉동 구분은 이력 데이터에 아예 없다.
2. **국내산/수입 API 라우팅 규칙** — 스캔된 번호가 소·돼지 API 대상인지 수입쇠고기 API 대상인지 판별하는 자릿수·접두어 기준 미정. 판별 불가 시 순차 호출 폴백 필요.
3. **캐시 TTL** — `fetched_at`만 두고 재조회 주기 규칙은 아직 없다. 등급·가공 정보가 나중에 갱신될 수 있어 영구 캐시는 위험.
4. **묶음번호 1:N 전개** — 묶음(15자리)이 개별 이력번호 여러 건을 포함하는 경우 마스터에 어떻게 펼쳐 저장할지 미정.
5. **공공 API 호출량 제어** — 서버리스는 인스턴스가 분산돼 메모리 기반 전역 레이트리밋이 불가능. 일일 한도를 지키려면 카운터 테이블이 필요.
6. ~~출고 연결~~ — **완료**(2단계). 다만 아래가 남는다:
   - **기존 운영 데이터에 대한 첫 확정 시 재고 급변 가능성** — 지금까지 수동 재고가 실제와 안 맞던 공급사는 첫 주문 확정에서 `INSUFFICIENT_STOCK`으로 막힐 수 있다. 배포 전 재고 정리 안내가 필요하다.
   - **`delivered` 이후 반품** — 현재 `delivered`에서 `cancelled`로 가는 전이가 없어(`ORDER_STATUS_TRANSITIONS`) 반품 재입고 경로가 아예 없다. 별도 이벤트(`ADJUSTMENT`/`LOSS`)로 처리해야 한다.
   - **부분 취소** — 현재 주문 취소는 전량 취소뿐이다. 부분 취소가 생기면 `reverse_order_shipment`를 수량 지정형으로 확장해야 한다.
   - **거래명세서 PDF 연결** — `get_order_trace_numbers()`는 만들었지만 아직 어느 화면·PDF에도 붙이지 않았다.
7. **중복 스캔 방지 정책** — 박스 단위 식별자 기반 dedupe 규칙 미정(이력번호+중량+시각 근접도 등).
8. **오프라인 대응** — 냉동창고 전파 불량 시 IndexedDB 로컬 큐 + 복구 시 동기화(PWA). 웹인 이상 스택과 무관한 별도 과제.

### 공공 API 커넥터 (6단계)

**`lib/livestock/mtrace-client.ts`** — 축산물이력제 오픈API 클라이언트.

- `MTRACE_API_KEY` 미설정이면 스캔이 막히지 않는다. 물건은 실제로 창고에 들어와 있으므로 입고는 받아들이고 `EXCEPTION`(사유 `API_ERROR`)으로 남긴다. 나중에 키를 넣고 예외 목록을 재조회하면 채워진다 — **현장을 세우지 않는 게 우선**이라는 판단이다.
- 엔드포인트와 응답 필드명이 **전부 미확정**이다(인증키 미발급). 그래서 `kape-client.ts`와 같은 전략을 쓴다 — 정확한 XML 경로에 의존하지 않고 트리를 재귀 탐색해 알려진 후보 키들을 찾는다. 원본은 `master_livestock.raw_payload`에 통째로 보관하므로, 실제 필드명이 확인되면 **캐시를 버리지 않고 파서만 고치면 된다.**
- `fast-xml-parser`의 `parseTagValue: false`를 반드시 유지할 것. 기본 설정은 `"00"` 같은 문자열을 숫자 `0`으로 바꾸는데, 이력번호는 0으로 시작하는 경우가 흔하다(`kape-client.ts`가 `resultCode "00"` 비교에서 이미 겪은 함정).
- **품목별 3갈래 라우팅** — 운영 기관이 서로 다르다(잠긴 결정):

  | 품목 | 기관 | 환경변수 |
  |---|---|---|
  | 국내산 소·돼지 | 축산물이력제 (mtrace.go.kr, 축산물품질평가원) | `MTRACE_API_KEY` |
  | 수입 축산물 | 수입축산물 이력관리시스템 (meatwatch.go.kr) | `MEATWATCH_API_KEY` |
  | 닭·오리·계란 | 가금류 이력관리시스템 | `POULTRY_TRACE_API_KEY` |

  번호 형식으로 1차 판별하고(12자리 → 개체, `L`+14자리/15자리 → 묶음, 영문 접두어 → 수입), 판별 실패 시 **설정된 기관만** 순서대로 시도한다. 키가 없는 기관은 오류가 아니라 건너뛴다 — 소·돼지만 취급하는 업체는 `MTRACE_API_KEY` 하나만 넣으면 되고 호출도 한 번만 나간다. 자릿수 규칙은 확정 스펙이 아니라 실호출로 재검증이 필요하다.
- **키 폴백**: 소·돼지 이력을 운영하는 곳은 축산물품질평가원(KAPE)으로, 이미 동작 중인 경락가 API(`data.ekape.or.kr`, `KAPE_MARKET_PRICE_API_KEY`)와 같은 기관이다. data.go.kr은 계정당 공용 인증키를 주므로, 전용 키를 안 넣으면 그 키로 먼저 시도한다 — **별도 발급 없이 바로 될 수 있고, 안 되면 예외로 남을 뿐이라 손해가 없다.**
- **오퍼레이션 이름을 몰라도 굴러가게 했다.** data.go.kr에서 받은 End Point는 서비스 기본 경로까지만이고(`http://data.ekape.or.kr/openapi-data/service/user/grade` — 경락가 API와 동일), 그 뒤에 붙는 오퍼레이션 이름은 활용가이드 문서를 봐야 안다. 문서 확인 전에도 쓸 수 있도록 **후보 주소를 순서대로 시도해 실제 이력이 담긴 응답을 찾고, 성공한 주소는 프로세스가 사는 동안 기억한다.** 정확한 주소를 알게 되면 `*_API_ENDPOINT`로 고정하는 게 좋다 — 후보 탐색이 사라져 첫 호출이 빨라진다.
- **받은 API는 "축산물등급판정정보"이지 "축산물이력정보"가 아니다.** 등급·도축일·도축장·축종은 여기서 나올 것으로 보지만 농장명·출생일·이동경로 같은 사육 이력은 별도 이력 API가 필요하다. 입고 검증에 필요한 핵심은 등급판정정보로 대부분 커버된다는 판단으로 먼저 붙였다.
- 엔드포인트 주소는 전부 추정값이라 `*_API_ENDPOINT` 환경변수로 덮어쓸 수 있게 해뒀다. 실호출로 확인한 주소가 생기면 **코드 수정 없이 `.env`만 고치면 된다.** 기본값은 경락가 API와 같은 도메인 체계(`data.ekape.or.kr`)로 맞춰뒀다 — 같은 기관이라 가장 가능성이 높다는 판단이다.
- **주소 검증은 이 개발 환경에서 불가능했다.** 아웃바운드 요청이 프록시에서 403으로 막혀 주소가 맞는지 틀린지 구분되지 않는다. 다만 `data.meatwatch.go.kr`만 연결 자체가 실패해 그 주소는 틀렸을 가능성이 크고, 수입 쪽은 `apis.data.go.kr` 경로로 바꿔뒀다(이것도 미확인).
- **양과 가공육은 이력제 대상이 아니다.** 스캔하면 예외로 남고 입고 자체는 정상 기록된다.
- 타임아웃 8초(`AbortController`). 현장 스캔이 무한정 매달리지 않게 한다.

**`app/dashboard/inbound/actions.ts`** — 스캔 Server Action.

- Lazy Loading 순서: 마스터 캐시 → (미스면) 공공 API → `upsert_master_livestock` → `record_inbound_scan`.
- 중복 의심이면 저장하지 않고 직전 스캔 시각(HH:MM)을 돌려준다. 작업자가 확인하면 `confirmDuplicate: true`로 다시 호출한다.
- 입고는 현장 작업이라 `staff`까지 허용한다(상품 마스터 수정은 `manager` 이상).

**환경변수**: `.env.example`의 `MTRACE_API_KEY` 참고. data.go.kr에도 같은 축산물이력 API가 올라와 있어, 그 경로로 쓴다면 기존 `NTS_BUSINESS_VERIFY_API_KEY`/`KAPE_MARKET_PRICE_API_KEY`와 동일한 data.go.kr 계정 공용키가 그대로 통할 수 있다 — **별도 발급 전에 먼저 시험해볼 것**(엔드포인트 주소도 함께 맞춰야 한다).

**미검증**: 실호출 전무. 엔드포인트 경로·파라미터명·응답 필드명 전부 문서 기준 추정이다. 특히 **부위(`partName`)가 응답에 실제로 오는지**가 매핑 자동화율을 좌우한다.

### 스캔 화면 (7단계)

**`/dashboard/inbound`** — 현장 입고 화면. 위에서 찍고 아래에 바로 쌓인다.

- **입력 흐름**: 바코드를 찍으면(HID 스캐너가 Enter를 보냄) 중량 칸으로 포커스가 넘어가고, 중량 입력 후 Enter로 등록된다. 등록 즉시 입력칸이 비고 이력번호 칸으로 돌아와 다음 박스를 바로 찍을 수 있다.
- **낙관적 UI**: 서버 응답을 기다리지 않고 목록에 "검증 중…" 행을 먼저 얹는다. 콜드 스타트나 공공 API 지연(최악 2~3초)이 현장 작업을 멈추지 않게 하려는 것이다.
- **카메라**: `npm` 레지스트리가 이 환경에서 막혀 `html5-qrcode` 같은 의존성을 추가할 수 없어, **브라우저 내장 `BarcodeDetector`** 를 쓴다. Android Chrome은 지원하고 iOS Safari는 아직 아니다 — 미지원 브라우저에서는 카메라 버튼을 감추고 스캐너/수동 입력만 노출한다(잠긴 결정: 의존성 추가가 가능해지면 재검토).
- **중복 경고**: DB가 `DUPLICATE_SUSPECTED`를 던지면 저장하지 않고 직전 스캔 시각을 담은 확인창을 띄운다. "다른 박스가 맞다"를 누르면 `confirmDuplicate`로 재호출한다.
- **상품 미확정**: `PENDING_MAPPING`/`EXCEPTION` 행에는 상품 선택 드롭다운이 붙는다. 한 번 고르면 `trace_product_map`에 학습돼 같은 부위는 다음부터 자동 연결된다.
- **인증키 미설정 안내**: 키가 하나도 없으면 상단에 "입고는 기록되지만 이력 검증이 안 된다"는 경고를 띄운다. 현장을 막지 않는다는 원칙을 화면에서도 밝힌다.

**`"use server"` 파일의 값 export 금지** — `STOCK_ADJUST_REASONS`를 `app/dashboard/products/actions.ts`에 두고 있었는데, Next.js는 `"use server"` 파일에서 async 함수 외의 export를 빌드 에러로 막는다. `lib/products/stock-adjust-reasons.ts`로 분리했다. 새 Server Action을 만들 때 같은 실수를 반복하지 말 것.

### 스캔으로 상품 자동 등록 (8단계)

처음 취급하는 고기를 찍으면 지금까지는 `PENDING_MAPPING`으로 남고, 공급사가 상품관리로 나가 상품을 만들고 입고 화면으로 돌아와 다시 골라야 했다. **공공 API가 이미 축종·부위·등급을 알려주는데 그걸 사람이 다시 입력하는 셈**이라 왕복 자체를 없앴다.

```
002123456789 스캔
  → 이력: 한우 / 등심 / 1++
  → "한우 등심 1++" 상품 자동 생성 + 입고 + 매핑 학습
  → 다음부터 같은 부위는 묻지도 않고 바로 입고
```

**잠긴 설계 결정:**

1. **축종과 부위가 둘 다 있을 때만 자동 생성한다.** 부위를 모르면 "한우 1++" 같은 반쪽 상품이 양산된다. 그 경우는 기존대로 되묻는다. (API가 부위를 안 줄 가능성이 커서 실제로는 되묻는 쪽이 더 잦을 수 있다 — 실호출로 확인 필요)
2. **판매가는 0으로 만든다.** 값을 대신 정해줄 수 없고, 0원 상품은 이미 고객에게 노출되지 않으므로(`20260930000058`) 안전하다. 공급사가 값을 매기는 순간 미니샵에 나타난다. 화면에서 "판매가를 넣어야 고객에게 보입니다"라고 안내한다.
3. **같은 조합(축종+부위+등급)이 이미 있으면 새로 만들지 않고 재사용한다.** 이름만 다르게 등록해 둔 경우까지는 못 잡지만, 스캔이 만드는 중복은 막는다.

상품명은 `한우 등심 1++`처럼 사람이 읽는 순서로 만든다 — 원문 축종(`species`, 예: 한우)이 있으면 그걸 쓰고 없으면 분류값(소)을 쓴다. 원산지는 수입이면 원산지 국가, 아니면 "국내산".

**검증 (4종 통과)**: 상품 0개 상태에서 스캔 → `PENDING_MAPPING` → 자동 생성 시 `한우 등심 1++`(소/등심/1++/국내산/0원/kg, 재고 8.20) → 같은 부위 재스캔 시 상품 추가 생성 없이 바로 `NORMAL`(재고 15.70) → 부위 없는 이력은 `INSUFFICIENT_TRACE_INFO`로 생성 안 함.

### 바코드 범용 파서 (9단계)

현장 박스 라벨은 한 가지가 아니다. 스캐너가 보내는 값이 셋 중 무엇이든 같은 결과를 내도록 `lib/livestock/barcode-parser.ts` 한 곳에서 해석한다.

| 형태 | 예 | 뽑아내는 것 |
|---|---|---|
| 순수 이력번호 | `002123456789` | 이력번호 |
| **GS1-128 물류 바코드** | `(01)088…(3103)008200(11)260813(251)002123456789` | 이력번호 + **중량 8.2kg** + 포장일 + 로트 + GTIN |
| 소비자용 QR | `https://mtrace.go.kr/…?traceNo=002123456789` | 이력번호 |

**GS1-128에는 중량이 들어 있다** — 이걸 읽어내면 작업자가 중량을 손으로 칠 필요가 없다. 바코드에 중량이 있으면 `Enter` 한 번으로 바로 등록된다(직접 입력한 값이 있으면 그쪽을 우선한다).

**설계 메모:**
- 모르는 AI를 만나면 거기서 멈추고 그때까지 읽은 것만 쓴다 — 잘못 잘라서 엉뚱한 값을 만드는 것보다 낫다.
- 어떤 경로로도 번호를 못 찾으면 문자열 전체에서 12자리/15자리 숫자를 찾는 폴백으로 내려간다.
- GS1 날짜는 2자리 연도라 50을 기준으로 세기를 가르고(GS1 규칙), 일자 `00`(미지정)은 그 달 1일로 본다.
- `raw`에 원본을 그대로 담아둔다 — 해석이 틀렸을 때 추적하려면 필요하다.

**검증 (2026-09-23, 15종으로 확장)**: 실제 스캔 원문은 물리 라벨이라 텍스트로 구할 수 없어서, GS1 공식 일반사양의 AI 인코딩 규칙대로 직접 구성한 경계 케이스로 검증했다. 기존 8종(순수/묶음 2형태/GS1 2형태/URL/잡음/빈값)에 7종 추가: 다른 소수점 자리(3102) + 실제 GS 구분자 포함, AI 순서가 뒤바뀐 경우, 이력번호 아닌 3자리 가변 AI(241)가 섞인 경우, **상자 단위 물류 라벨(AI 00, SSCC)**, 안 쓰는 계량단위(320n=lb) 무시.

이 중 SSCC 케이스에서 실제 버그를 발견해 수정했다 — `looksLikeGs1()`이 "AI 01(GTIN)로 시작하거나 괄호 표기이거나 구분자(GS)가 있는 경우"만 GS1로 인식했는데, **AI 00(SSCC)으로 시작하면서 뒤따르는 필드가 전부 고정길이라 구분자가 아예 없는 경우** 이 셋 중 아무것도 해당하지 않아 GS1 판별 자체가 실패했다. 실패하면 "순수 숫자 폴백"으로 내려가는데, 그 폴백은 전체가 숫자로 이어붙은 문자열에서 정확히 12/15자리 경계를 못 찾아 결국 `traceNo: null`이 됐다 — **여러 박스가 든 겉상자(팔레트/케이스) 단위로 오는 물류 라벨을 통째로 놓치는 사고**였다. `startsWithKnownAi()`로 바꿔 `FIXED_LENGTH_AI`에 등록된 AI(00 포함)·가변길이 AI(10/21/240/241/251)·계량 AI(3xx)를 전부 인식하도록 일반화해 수정.

**로트번호(lotNo) 검증 구멍도 발견해 고쳤다** — 검증 루프가 `traceNo`/`weightKg`/`packingDate`/`format` 네 개만 고정으로 체크하고 있어서, 케이스 데이터에 `lotNo`/`bestBefore`/`gtin`을 적어둬도 실제로는 비교가 안 되고 통과 표시가 났다. 케이스에 적힌 필드를 전부 동적으로 검증하도록 바꾸고 재실행 — 15건 여전히 전부 통과(로트번호 `LOT999`/`LOTXYZ`도 정확히 추출됨), 숨어 있던 파서 버그는 없었다.

같은 세션에서 테스트 실행 자체가 막히는 별개 문제도 발견해 고쳤다 — `scripts/lib-strip-types.mjs`가 타입 제거에 리터럴 `\n`(LF) 기준 정규식을 쓰는데, 이 저장소를 Windows에 체크아웃하면 CRLF라 `interface`/`export type` 블록이 하나도 안 지워져 `new Function()` 평가가 문법 오류로 죽었다(이번 세션에서 이 스크립트를 처음 실제로 돌려서 드러남 — 원래 검증은 다른 환경에서 실행됐던 것으로 보인다). `stripTypes()` 맨 앞에서 `\r\n` → `\n` 정규화 한 줄 추가로 해결 — 이 저장소의 `evaluateModules` 기반 테스트 스크립트 전부(바코드/엑셀 파서/가격 CSV/중량오차)에 공통 적용됨.

실제 박스 라벨로는 아직 확인 못 했다.

### 입출고 내역 한 화면 (10단계)

**`/dashboard/stock-ledger`** — 입고·출고·조정·손실이 한 곳에 시간순으로 쌓인다. 재고 숫자가 왜 그렇게 됐는지 여기서 추적한다.

지금까지는 입고는 입고 스캔 화면, 출고는 발주 관리, 조정은 기록만 남고 목록이 없어 흩어져 있었다. 원장(`stock_ledger`)에 이미 전부 모이고 있었으므로 **조회만 붙였다** — 새 데이터는 없다.

```
09/22 14:30  [입고]  한우 등심  002111111111            A사장   +8.2kg  → 8.2kg
09/22 14:35  [입고]  한우 등심  002222222222            A사장   +7.5kg  → 15.7kg
09/22 16:00  [손실]  한우 등심  폐기 — 일부 폐기        A사장   -0.3kg  → 15.4kg
09/22 15:10  [출고]  한우 등심  002111111111  ORD-001   A사장   -5.0kg  → 10.4kg
```

**오래된 순으로 정렬하고 줄마다 그 시점 재고(→)를 붙인다.** 원장을 읽는 목적이 "재고가 왜 이 숫자인지" 추적이라, 누적을 따라 읽으려면 오래된 것부터가 맞다.

시점 재고 계산에서 조심한 것 두 가지:
- **상품별로 누적한다.** 여러 상품이 섞인 목록에서 전체를 누적하면 의미 없는 숫자가 나온다.
- **필터 적용 전에 누적한다.** 기간·유형 필터를 건 뒤 누적하면 구간 시작 전 재고가 빠져 0부터 시작해버린다. 그래서 전체 행에서 누적을 먼저 구하고 나중에 걸러낸다 — 출고만 필터해도 시점 재고는 전체 기준으로 맞게 나온다.

- 필터: 기간(기본 최근 30일)·상품·유형·**이력번호**. **URL 쿼리로 유지**해서 새로고침·뒤로가기에도 조건이 살아 있고 링크로 공유된다.
- **이력번호 검색**으로 "이 번호가 언제 들어와서 어디로 나갔나"를 한 줄로 따라간다. 출고 행에도 `inbound_scan_id`가 있어(어느 박스가 나갔는지 기록) 같은 번호로 입고와 출고가 함께 잡힌다 — 그게 이 검색의 목적이다. 번호 일부만 입력해도 찾는다.
  - 이력번호 필터는 **누적 계산 뒤에** 적용한다. 계산 전에 걸러내면 그 박스 행만 남아 시점 재고가 상품 전체가 아니라 박스 하나의 누적이 돼버린다.
  - 다른 필터와 달리 타자마다 주소를 바꾸면 화면이 깜빡여서 Enter나 검색 버튼으로만 적용한다.
  - 조회는 입고 스캔 화면이 아니라 여기에 모았다 — 입고 화면은 현장에서 찍는 데 집중하는 화면이라 검색창이 방해가 된다(잠긴 결정).
- 상단에 기간 요약(입고/출고/조정/손실 합계).
- 목록에서 상품명·이력번호·주문번호·작업자를 각각 조회하면 N+1이라 `list_stock_ledger()`가 조인해서 한 번에 내려주고, 총건수도 같이 준다.
- 원장은 계속 쌓이기만 하므로 기본 구간을 최근 30일로 두고 한 번에 200건까지만 가져온다.

**검증 (8종 통과)**: 입고 2건 + 손실 1건 + 출고 1건이 오래된 순으로 시점 재고(8.20 → 15.70 → 15.40 → 10.40)와 함께 조회됨 / 기간 요약(입고 15.70, 출고 -5.00, 손실 -0.30) / **출고만 필터해도 시점 재고가 전체 기준 10.40 유지** / 마지막 시점 재고가 `products.stock_quantity`와 일치 / 다른 업체 계정은 0건 / **이력번호 검색 시 같은 번호의 입고+출고가 함께 조회되고 시점 재고는 상품 전체 기준 유지** / 번호 일부(`0021111`)만으로도 2건 조회 / 다른 번호는 해당 1건만.

### 카카오톡 채널 진입 (11단계)

카카오톡 채널 하단 메뉴의 `[상품입고]` 버튼이 가리키는 중간 페이지 **`/go/inbound`**.

**왜 중간 페이지가 필요한가:** 채널 버튼을 누르면 카톡 인앱 브라우저가 열리는데, **거기서는 카메라 접근이 막히는 경우가 많아** 바코드 카메라 스캔이 동작하지 않는다. 블루투스 스캐너와 수동 입력은 되지만 카메라만 쓰는 현장은 막힌다.

```
카톡 채널 [상품입고] → /go/inbound
   ├ 일반 브라우저   → /dashboard/inbound 로 즉시 이동 (중간 화면 안 보임)
   ├ 카톡 인앱       → kakaotalk://web/openExternal 로 기본 브라우저 열기 + 안내
   └ 기타 인앱       → 수동 안내 ("⋯ → 다른 브라우저로 열기")
```

- 카카오가 제공하는 `kakaotalk://web/openExternal?url=` 스킴은 **iOS·안드로이드 공통**이라 한 줄로 양쪽이 해결된다. 동작하지 않아도 안내 화면이 그대로 남아 수동으로 열 수 있다.
- **이 경로는 로그인 가드 밖**이다(`middleware.ts`의 `SUPPLIER_PREFIXES`는 `/dashboard`만 막는다). 로그인 전에도 열려야 브라우저를 먼저 바꾸고 거기서 로그인할 수 있기 때문이다.
- 일반 브라우저에서는 `location.replace`로 넘겨 **뒤로가기가 이 페이지로 되돌아오지 않게** 한다.
- 안내 화면에 **"홈 화면에 추가"** 를 권한다. 카톡을 매번 거치는 것보다 바탕화면 아이콘이 현장에서 훨씬 빠르고, 로그인도 유지된다 — **카톡 버튼은 최초 진입용, 일상은 홈 화면 아이콘**이라는 판단이다(잠긴 결정).

**남은 이슈:** 카톡 인앱 → 외부 브라우저로 나가면 **세션 쿠키가 따라가지 않아 다시 로그인**해야 한다. 브라우저에 한 번 로그인하면 그 뒤로는 유지되므로 최초 1회만 겪는다. 매번 겪는 문제가 된다면 거래명세서에서 쓴 서명 토큰 방식(`DOCUMENT_LINK_SECRET`)을 재사용해 우회할 수 있다 — 실제로 문제가 되는지 배포 후 확인하고 판단한다.

**검증**: UA 판별 7종(카톡 안드로이드·iOS, 네이버, 인스타그램, Chrome, Safari, PC) 통과. 실기기에서는 아직 확인 못 했다.

### 자동 생성 운영에서 드러난 구멍 수정 (12단계)

자동 등록을 붙이고 나서 네 가지가 걸렸다.

**1. 입출고 기록이 있는 상품은 삭제할 수 없다** ← 실제 버그
`stock_ledger.product_id`가 `ON DELETE RESTRICT`다(입출고 기록은 지우면 안 되는 자료). 한 번이라도 입출고가 있으면 `DELETE`가 외래키 위반으로 실패한다. 오스캔으로 엉뚱한 상품이 하나 생기면 목록에서 영영 못 치운다.

→ **보관(`products.archived_at`)** 을 도입했다. 기록은 남고 목록·미니샵에서만 사라진다. 삭제 버튼은 기록이 있으면 DB가 막기 전에 미리 확인해 *"입출고 기록이 있는 상품은 삭제할 수 없습니다 — 대신 '보관'으로 감출 수 있습니다"* 로 안내한다. **보관하면 판매도 함께 내린다** — 목록에서 감췄는데 미니샵에 남아 있으면 사고다.

**2. 상품이 폭증한다 — 이건 과한 우려였다(철회)**
등급×부위 조합은 이론상 수십 개지만 **실제로는 들어오는 것만 생긴다.** 초기 며칠 몰리고 그 뒤로는 거의 늘지 않는다. 대신 아래 3번 필터로 완화한다.

**3. 판매가 0원 상품이 섞여 진짜 파는 상품이 묻힌다**
→ 상품 목록에 **상태 필터**를 뒀다: `전체(보관 제외)` / `판매중만` / `판매가 미설정(n)` / `보관함`. 기본은 보관을 뺀 전체다 — 보관은 치운 상품이라 기본 목록에 섞이면 안 된다.

**4. 자동 생성 상품이 '판매중'이라 가격만 넣으면 즉시 팔린다**
아직 팔 준비가 안 됐는데 주문이 들어올 수 있다.
→ 자동 생성은 **판매중지**로 만든다. 공급사가 가격을 넣고 직접 켜야 노출된다. 스캔 화면 안내도 *"판매가를 넣고 '판매중'으로 바꿔야 고객에게 보입니다"* 로 바꿨다.
→ 보관돼 있던 같은 조합을 다시 찍으면 새로 만들지 않고 **보관만 풀어** 재사용한다(판매 여부는 공급사가 정한다).

**검증 (5종 통과)**: 자동 생성 시 판매중지+0원 / 기록 있는 상품 삭제가 외래키로 차단됨 / 보관 시 판매 함께 내려감 / 보관 상품은 고객에게 0건 / 복원 후 판매중 전환하면 다시 1건.

### 엑셀 대량 입고 (13단계)

입고 화면의 **엑셀 대량 입고** 패널. 한 번에 최대 5,000행.

**입력 경로 두 가지** — npm 레지스트리가 이 환경에서 막혀 SheetJS 같은 `.xlsx` 파서를 넣을 수 없다. 대신 엑셀에서 바로 나오는 형태를 받는다(잠긴 결정: 의존성 설치가 가능해지면 `.xlsx` 직접 파싱 재검토):

1. **CSV 파일** (엑셀 > 다른 이름으로 저장 > CSV)
2. **엑셀에서 범위 복사 → 붙여넣기** (탭 구분) — 실무에서 더 빠르다

`.xlsx`를 고르면 "CSV로 저장하거나 복사해 붙여넣어달라"고 안내한다.

**파싱** (`lib/livestock/import-parser.ts`)
- 구분자(탭/쉼표/세미콜론)를 첫 줄로 자동 판별하고, 따옴표로 감싼 칸 안의 구분자를 지킨다.
- 머리글 줄은 자동으로 건너뛴다(첫 칸에서 이력번호를 못 뽑고 글자가 섞여 있으면 머리글로 본다).
- 첫 칸은 **바코드 값 그대로도 된다** — `barcode-parser`를 태우므로 GS1-128이나 QR이 셀에 들어있어도 이력번호를 뽑아낸다. 엑셀에 스캐너로 찍어 넣은 값이 그대로 있는 경우가 흔하다.
- 중량은 둘째 칸을 먼저 보고, 없으면 바코드에 실려 있던 값을 쓴다. `8.2kg`, `8,2` 같은 표기도 읽는다.
- 읽을 수 없는 줄은 업로드에서 빼고 화면에 줄 번호와 이유를 보여준다.

**처리** — 브라우저가 청크를 반복 호출한다(Hobby 크론 제약, 8단계 참고).
- 한 번 호출의 **시간 예산 6초**, 최대 25행. 건수가 아니라 시간으로 끊는 이유는 이력 조회가 붙은 행이 느려서다 — 캐시에 있는 행은 수십 건도 금방 지나가고, 전부 새 번호면 몇 건에서 끊긴다.
- 창을 닫아도 작업이 DB에 남아 다시 들어오면 **"이어서 처리"** 로 재개된다.
- **엑셀 경로는 중복 검사를 건너뛴다** — 한 파일에 같은 규격이 여러 줄 있는 게 정상이고 행마다 확인창을 띄울 수도 없다. 바코드 스캔은 그대로 경고한다.

**검증 (4종 통과)**: 작업·행 생성 / 엑셀 경로는 같은 번호+같은 중량도 통과해 재고 16.40 / 같은 값이라도 바코드 스캔이면 `DUPLICATE_SUSPECTED` / 다른 업체는 작업·행 모두 0건. 파서는 `node scripts/test-import-parser.mjs` 6종(CSV+머리글, 탭 붙여넣기, 단위 표기, GS1 셀, 오류 줄 혼재, 빈 입력) 통과.

### 판매가 일괄 등록 (14단계)

스캔으로 자동 등록된 상품은 판매가가 0원이라 고객에게 안 보인다. 수십 개를 화면에서 하나씩 고치는 건 고통스러워서, 상품관리에 **내려받기 → 엑셀에서 채우기 → 올리기** 경로를 뒀다.

내려받는 CSV에는 **공공 시세가 참고로 들어간다** — 값을 매길 때 옆에 두고 보라는 것이다.

**잠긴 설계 결정:**
1. **상품 식별은 UUID로만 한다.** 이름으로 맞추면 같은 이름이 둘이거나 엑셀에서 이름을 고친 순간 엉뚱한 상품 가격이 바뀐다. CSV에 `상품ID` 칸을 넣고 건드리지 말라고 안내한다.
2. **빈 칸·0·음수는 "입력 안 함"으로 보고 건너뛴다.** 실수로 지운 칸 때문에 멀쩡한 가격이 0이 되면 그 상품이 고객에게서 사라진다.
3. **판매중 전환은 선택이다.** 가격만 넣고 아직 팔지 않을 수도 있다. 전환하더라도 가격이 들어간 상품만 켠다.
4. **망가진 줄 하나가 전체를 실패시키지 않는다.** ID가 깨진 줄은 세어서 보고하고 나머지는 반영한다.

읽을 때는 **칸 이름으로 찾는다**(`상품ID`, `판매가`) — 사용자가 열 순서를 바꾸거나 메모 열을 추가해도 동작한다. CSV에 BOM을 붙여 엑셀에서 한글이 깨지지 않게 한다.

**검증 (4종 통과)**: 2건 반영 + 판매중 전환 / 빈 칸·0·음수는 기존 가격 보존 / 남의 상품·보관 상품은 반영 안 됨(`not_found`) / 망가진 ID가 섞여도 나머지는 반영. CSV 만들기·읽기는 `node scripts/test-price-import.mjs` 10종 통과.

### 출고 스캔 (15단계)

**`/dashboard/outbound`** — 나갈 박스를 찍어 **실제로 집은 박스로 배정을 정정**한다.

주문을 확정하면 `apply_order_shipment()`가 선입선출로 박스를 골라 차감한다. 그런데 그건 **추정**이다 — 현장 작업자가 실제로 집는 박스는 다를 수 있고, 그러면 장부와 실물이 어긋난다. 거래처에 "이 이력번호 고기를 드렸다"고 말할 근거도 사라진다.

```
확정 시 자동 배정   박스A 8.2 + 박스B 1.8  (선입선출 추정)
       ↓ 작업자가 박스C를 집어 스캔
출고 스캔 정정      박스C 6.0 + 박스B 4.0  (실제)
       → 박스A 잔량 8.2 복원, 재고 총량은 그대로
```

**잠긴 설계 결정:**
1. **원장은 고쳐 쓰지 않는다.** 되돌림(`OUTBOUND_UNASSIGN` +)과 재기록(`OUTBOUND_ASSIGN` −)으로 표현한다. 기존 행을 UPDATE하면 "언제 무엇이 바뀌었나"가 사라진다.
2. **되돌림은 주문당 한 번만.** 두 번째 박스를 찍을 때 또 되돌리면 앞서 스캔한 배정까지 풀린다.
3. **주문에 없는 상품의 박스는 거부**(`PRODUCT_NOT_IN_ORDER`). 엉뚱한 박스를 찍었을 때 조용히 넘어가면 재고가 틀어진다.
4. **주문 수량을 넘겨 배정하지 않는다**(`PRODUCT_ALREADY_FULFILLED`). 남은 필요량까지만 가져간다.
5. **확정·배송중 상태만 출고 대상**이다. 접수대기는 아직 확정 전, 완료·취소는 끝난 건이다.

- 입고와 같은 바코드 파서를 태운다 — GS1-128이나 QR을 찍어도 되고, **바코드에 중량이 실려 있으면 그만큼만** 가져간다(박스를 통째로 쓰지 않는 경우).
- `get_order_trace_numbers()`는 **출고 스캔이 있었으면 그것만, 없으면 자동 배정분**을 돌려준다 — 거래명세서에 찍히는 이력번호가 사실이 된다.
- 기간 요약의 "출고"에 `OUTBOUND_ASSIGN`/`UNASSIGN`을 포함시켰다. 빠뜨리면 스캔으로 나간 양이 어느 칸에도 안 잡혀 합계가 안 맞는다.

**검증 (8종 통과)**: 확정 시 선입선출 자동 배정(A 8.2 + B 1.8) / 작업자가 C를 찍으면 A 잔량 8.2 복원 + C 6.0 배정 / 남은 4kg을 B에서 채움 / **재고 총량 불변(11.70)** / 거래명세서 이력번호가 실제 스캔분(C 6.0, B 4.0)만 / 초과 배정 차단 / 주문에 없는 상품 차단 / 기간 요약 출고 합계 −10.

### 소분 출고 라벨 (16단계)

**`/dashboard/outbound/labels/[orderId]`** — 소분해서 나가는 봉지에 붙일 라벨.

박스를 통째로 주지 않고 잘라서 줄 때, **박스에 붙어 있던 라벨은 창고에 남는다.** 그런데 나가는 봉지에도 원래 이력번호를 표시해야 하므로(이력제) 새 라벨이 필요하다. 시스템은 수량을 정확히 추적하고 있었지만 **물리적 라벨이 비어 있던 자리**다.

라벨 한 장에 들어가는 것: 상품명 · 원산지 · 등급 · **중량** · **바코드** · **이력번호(큰 글자)** · 도축일 · 포장일 · 도축장 · 공급사 → 거래처 · 발주번호.

**바코드는 라이브러리 없이 직접 그린다**(`lib/livestock/code128.ts`) — npm 레지스트리가 이 환경에서 막혀 있다. Code 128-B를 SVG로 만든다.

⚠️ **실제 스캐너로 읽어본 적이 없다.** 표 전사 오류를 잡으려고 "모든 패턴은 11모듈(정지만 13)"이라는 규격 불변식을 코드에서 검사하지만(`validatePatternTable()`), 그게 판독을 보장하지는 않는다. **현장 배포 전에 스캐너로 한 장 찍어볼 것.** 바코드가 안 읽혀도 이력번호가 큰 글자로 함께 찍히므로 **표시 의무 자체는 충족되고** 사람이 옮겨 적을 수 있다.

### 부위 불일치 경고 (17단계)

입고 때 박스를 엉뚱한 상품에 매핑하면 **그 뒤로는 아무도 못 잡는다.** 출고 스캔은 "주문에 있는 상품인가"만 보므로, 채끝 박스가 등심 상품에 매핑돼 있으면 등심 주문에 그대로 통과한다 — 식당에는 채끝이 간다.

박스의 이력 정보에는 **진짜 부위**가 들어 있다. 그걸 상품의 `subcategory`와 대조해 입고·출고 양쪽에서 알린다.

```
이력 부위: 채끝    상품 부위: 등심
  ⚠️ 이 박스의 이력 부위는 '채끝'인데 상품은 '등심'입니다. 박스를 다시 확인해주세요.
```

**잠긴 설계 결정:**
1. **막지 않고 경고만 한다.** 부위 표기가 API와 우리 분류에서 다를 수 있고, 실제로는 맞는데 막으면 현장이 멈춘다.
2. **서로 포함 관계면 일치로 본다** — `"채끝"` vs `"채끝등심"`은 통과. 표기 차이로 헛경고가 쏟아지면 아무도 경고를 안 읽게 되고, **그게 경고가 없는 것보다 나쁘다.**
3. **한쪽이라도 모르면 경고하지 않는다.** 이력에 부위가 없는 경우가 흔한데 그때마다 경고하면 소음만 된다.
4. **입고는 사람이 직접 고른 경우에만 대조한다.** 학습된 매핑으로 자동 연결된 건은 이미 한 번 사람이 확인한 결과다.

**검증 (3종 통과)**: 이력 `채끝` + 상품 `등심` → 경고 / 이력 `채끝` + 상품 `채끝등심` → 경고 없음 / 출고 스캔에서도 같은 경고. 대조 규칙 자체도 4종 확인(`채끝등심`vs`채끝` false, `채끝`vs`등심` true, NULL false, 공백 차이 false).

### 피킹 목록 (18단계)

출고 스캔은 **찍은 뒤에야** 맞다/틀리다를 말해준다. 어느 박스를 가져와야 하는지는 작업자가 창고에서 알아서 찾았고, 오래된 박스가 뒤에 묻혀 있으면 손 닿는 새 박스부터 나가 결국 묵은 게 남았다.

발주서를 열면 **가져올 박스**를 선입선출 순서로 먼저 보여준다.

```
가져올 박스  (오래된 박스부터)
  한우 등심  1++                      8.2kg
  002111111111                       가져오기
  도축 2026-09-17 · 박스 8.2kg
  ---
  한우 등심  1++                      1.8kg
  002222222222                       가져오기
  도축 2026-09-19 · 박스 7.5kg
```

박스 전체 중량이 아니라 **이 주문에 필요한 만큼**을 보여준다(위의 두 번째 박스는 7.5kg짜리지만 1.8kg만 쓴다).

**잠긴 설계 결정:**
1. **출고 스캔 전/후로 계산 기준이 다르다.**
   - **스캔 전**: 주문 확정 때 `apply_order_shipment()`가 이미 선입선출로 박스를 골라 차감해 뒀다. 그 `ORDER_OUT` 배정이 곧 추천이다. 이때 박스 잔량은 **이미 깎여 있으므로** 가용 박스를 다시 훑으면 엉뚱한 답이 나온다.
   - **스캔 후**: 첫 출고 스캔이 자동 배정을 통째로 되돌렸으므로(15단계), 남은 필요량을 현재 가용 박스에서 선입선출로 다시 계산한다.
2. **이미 찍은 박스도 목록에 남기되 표시한다**(`already_picked`). 목록에서 사라지면 작업자가 "내가 이걸 찍었던가"를 기억해야 한다. 회색으로 죽이고 맨 아래로 내린다.
3. **추천은 추천일 뿐 강제하지 않는다.** 다른 박스를 찍어도 출고 스캔은 그대로 받는다 — 현장에서 추천 박스가 안 보이거나 상태가 나쁠 수 있다.

**DB**: `get_picking_list(p_order_id)` (`supabase/migrations/20260930000067_picking_list.sql`). 세 갈래(`from_auto` / `from_remaining` / `already`)를 `UNION ALL` 하고 `already_picked`, `scanned_at` 순으로 정렬한다. 남은 필요량 계산은 윈도 함수 누적합(`SUM(remaining_weight) OVER (PARTITION BY product_id ORDER BY created_at, id ROWS UNBOUNDED PRECEDING)`)으로 박스 경계를 자른다.

**화면**: `/dashboard/outbound` — 발주서를 고르면 출고 진행 위에 뜬다. 진행 상황과 같은 시점에 다시 불러온다(스캔 1건마다 갱신).

**검증 (`scripts/db-test-picking-list.sql`, 6종 통과)**: 스캔 전 추천이 확정 배정과 같다(A 8.2 + B 1.8 + 채끝 3) / 추천을 무시하고 최신 박스를 찍어도 남은 4kg이 가장 오래된 박스로 다시 잡힌다 / 찍은 박스는 `already_picked`로 맨 아래 / 다 채운 상품은 추천에서 빠진다 / 전부 채우면 추천이 비고 찍은 것만 남는다 / 남의 주문은 0행(RLS).

### 중량 정밀도 g 단위 (19단계)

바코드는 **g 단위로 온다.** GS1-128 계량 AI `3103`은 소수점 3자리라 `008204` → 8.204kg이고, 파서도 그걸 제대로 읽어냈다. 그런데 저장하는 컬럼이 전부 `NUMERIC(10,2)`라 둘째 자리에서 반올림됐다.

```
8.204kg → 8.20kg   (4g 증발)
8.206kg → 8.21kg   (4g 생성)
```

박스당 최대 5g. 하루 100박스면 500g — 한우 1++ 기준 하루 3~4만원이 장부에서 어긋난다. **방향이 랜덤이라 서로 상쇄되기도 하는데, 그래서 더 아무도 못 잡는다.**

**잠긴 설계 결정:**
1. **kg 단위를 유지하고 소수 자릿수만 늘린다**(`NUMERIC(10,3)`). g 정수로 바꾸면 기존 데이터·화면·API 전부가 1000배 변환을 타야 하고, 한 군데만 빠뜨려도 재고가 1000배로 틀어진다.
2. **금액 컬럼은 안 건드린다.** 원 단위 이하는 쓰지 않는다.
3. **RPC 안의 지역변수도 같이 올린다.** 컬럼만 올리면 계산 도중 `NUMERIC(10,2)` 변수를 거치며 도로 반올림된다 — 컬럼이 3자리를 받아도 들어가는 값이 이미 깎여 있다. `apply_order_shipment`(3개), `adjust_product_stock`(2개), `record_outbound_scan`(4개)을 재생성했다.

**대상 컬럼**: `products.stock_quantity`, `order_items.quantity`, `inbound_scans.weight`/`remaining_weight`, `stock_ledger.qty_delta`, `inbound_import_rows.weight` (`supabase/migrations/20260930000068_weight_precision_grams.sql`)

### 출고 마감 확인 (20단계)

10kg 주문에 9.7kg만 나가도 **아무 일이 없었다.** 경고 하나 없이 명세서에 10kg이 찍히고 680,000원이 청구됐다. `allDone` 플래그가 초록 글씨를 띄우긴 했지만 부족한 채로 배송 상태로 넘어가는 걸 막는 코드는 없었다. 축산은 박스가 딱 안 떨어지는 게 예외가 아니라 일상이라 이게 매 건 조금씩 쌓인다.

출고를 끝낼 때 **차이를 보여주고 사람이 승인해야** 넘어간다. 승인하면 그 순간 금액이 실제 중량 기준으로 확정된다.

```
⚠️ 주문보다 적게 나갔습니다
   한우 등심   주문 9kg / 실제 8.204kg  (-0.796kg)
               612,000원 → 557,872원
   [ 이대로 마감 ]   [ 더 스캔하기 ]
```

**잠긴 설계 결정:**
1. **주문 수량(`order_items.quantity`)은 고치지 않는다.** 고객이 무엇을 주문했는지는 증거다. 실제 나간 양은 `shipped_quantity`에 따로 쓴다.
2. **재고 원장은 건드리지 않는다.** 이미 사실대로 적혀 있다 — 출고 스캔이 자동 배정을 되돌리고(`OUTBOUND_UNASSIGN`) 실제 박스만 배정했으므로(`OUTBOUND_ASSIGN`) 8.204kg만 빠진 상태다. **틀렸던 건 재고가 아니라 돈과 서류뿐이다.**
3. **부족분은 사람이 확인해야만 통과한다**(`p_confirm_short`). 조용히 깎으면 "왜 청구액이 다르냐"는 분쟁이 나중에 터진다. 화면에서 차이를 보여주고 누른 것이 근거가 된다.
4. **한 상품이 여러 줄로 주문된 경우 줄 순서대로 채운다.** 비율 안분은 원 단위 반올림 오차로 합이 안 맞는다.
5. **초과 출고는 애초에 안 생긴다** — `record_outbound_scan()`이 주문 수량을 넘겨 배정하지 않는다. 그래도 방어적으로 `LEAST`를 건다.

**DB**: `preview_order_shipment(p_order_id)`(조회만), `finalize_order_shipment(p_order_id, p_confirm_short)` (`supabase/migrations/20260930000069_finalize_shipment.sql`). 실제 출고량 기준은 `get_order_trace_numbers()`와 동일하다 — 출고 스캔이 있었으면 `OUTBOUND_ASSIGN`, 없으면 `ORDER_OUT`.

**화면**: `/dashboard/outbound`의 "출고 마감" 버튼. 부족하면 `SHIPMENT_SHORT`를 받아 확인 패널을 띄우고, "이대로 마감"이 `p_confirm_short=true`로 다시 부른다.

**거래명세서**: `lib/orders/statement.ts`가 `shipped_quantity ?? quantity`를 찍는다. 마감 전이면 주문량이 그대로 나가고, 마감 후에는 실제 중량과 확정 금액이 함께 맞는다.

**검증 (`scripts/db-test-finalize-shipment.sql`, 8종 통과)**: 8.204kg이 반올림 없이 저장 / 스캔 전 미리보기는 차이 0 / 8.204만 찍으면 -0.796 표시 / 확인 없이 마감하면 `SHIPMENT_SHORT` / 확인하면 557,872원으로 확정되고 주문 수량 9는 그대로 / 재고는 1.496 유지(원장 무변경) / 두 번 마감은 `ALREADY_FINALIZED` / 남의 주문은 0행.

### 거래명세서에 이력번호 (21단계)

축산물이력제상 판매 시 이력번호를 알려야 하는데, **출고 스캔으로 어느 박스가 나갔는지 다 알면서도 명세서에는 안 찍혔다.** `get_order_trace_numbers()`는 15단계에서 이미 만들어 뒀고 연결만 안 돼 있었다.

품목표 아래에 별도 블록으로 들어간다.

```
축산물 이력번호 (실제 출고 박스 기준)
  한우 등심   002111111111   8.204   1++ · 2026-09-17 · ○○도축장
  한우 등심   002222222222   1.496   1++ · 2026-09-19 · ○○도축장
```

**잠긴 설계 결정:**
1. **어느 박스가 나갔는지 고르는 기준은 DB 함수 하나에 둔다.** 출고 스캔이 있으면 `OUTBOUND_ASSIGN`, 없으면 `ORDER_OUT`. 명세서와 출고 화면이 서로 다른 답을 내면 안 된다.
2. **못 불러와도 발행은 막지 않는다.** 이력번호는 명세서의 부가 정보다. 공급사 주소 누락(`findMissingStatementFields`)과 달리 문서 자체를 무효로 만들지 않는다.

**파일**: `lib/orders/statement.ts`(`fetchTraces`), `lib/pdf/transaction-statement.tsx`. 공급사/바이어 양쪽 로더가 같이 쓴다 — 인가는 RPC 안에서 처리된다.

### 유통기한 (22단계)

GS1-128 바코드에는 유통기한(AI 17)과 품질유지기한(AI 15)이 실려 온다. **파서는 이미 `bestBefore`로 읽어내고 있었는데 저장할 컬럼이 없어 그대로 버려졌다.**

**잠긴 설계 결정:**
1. **유통기한은 `master_livestock`이 아니라 `inbound_scans`에 둔다** — 박스 속성이지 이력번호 속성이 아니다. 같은 이력번호라도 가공·포장 시점이 다르면 기한이 다르다. (포장일 `packing_date`가 master에 있는 건 그게 공공 API에서 오는 이력 정보라서다. 유통기한은 **API가 주지 않고 바코드에만 있다.**)
2. **기한이 지난 박스는 출고를 막는다**(`BOX_EXPIRED`). 부위 불일치는 표기 차이로 헛경고가 날 수 있어 경고만 했지만, 기한 경과는 판단의 여지가 없고 식품위생법 위반이다. **확인 버튼으로 넘길 수 있게 만들면 안 된다.**
3. **입고는 막지 않는다.** 이미 지난 물건이 들어왔다면 그 사실을 기록해야 반품·폐기 처리가 된다. 스캔을 거부하면 장부에 아무것도 안 남는다. 대신 그 자리에서 경고한다.
4. **피킹 순서는 입고순(FIFO)을 유지하고 기한은 표시만 한다.** 기한순 출고(FEFO)로 바꾸는 건 별개의 큰 변경이라 여기서 섞지 않는다. 대부분 입고순과 기한순은 같다.

**구조상 주의**: `record_inbound_scan`에 파라미터가 하나 더 붙어 시그니처가 9개가 됐다. 본문을 통째로 다시 쓰면 중복 감지·자동 매핑 규칙을 또 복제하게 되므로, 기존 8개짜리 본문을 `record_inbound_scan_base`로 옮기고 새 함수가 그걸 부른 뒤 기한만 덧붙인다. 호출 모호성을 없애려 원래 이름의 8개짜리는 `DROP`한다.

**DB**: `inbound_scans.best_before` + 부분 인덱스, `get_expiring_boxes(p_days)`, `record_inbound_scan`/`record_outbound_scan`/`get_picking_list` 갱신 (`supabase/migrations/20260930000070_best_before.sql`)

**화면**: 입고 스캔은 지난 박스면 빨간 경고("입고는 기록했지만 출고되지 않습니다"), D-3 이내면 안내. 출고 스캔은 지난 박스를 날짜와 함께 거부하고, 임박 박스는 경고를 띄운다. 피킹 목록에도 남은 일수를 표시한다.

### 자체 세트 상품 (BOM) + 이력 역추적 (23단계)

**`/dashboard/bundles`** — 도매업체가 임의로 묶은 세트("삼겹살+목살 실속세트")를 플랫폼 안에서
자체 상품코드·세트번호로 발행하고, **그 박스에 실제로 들어간 고기의 정부 이력번호를 1:N으로
묶어 남긴다.** 이력 추적 요청이 들어왔을 때 세트번호 하나로 원본까지 거슬러 올라간다.

```
BND-0001  삼겹살+목살 실속세트 (삼겹살 2kg + 목살 1kg)
   │  세트 제작 2세트
   ├─ SET-260922-001  3.0kg   ← 002111111111 삼겹 2.0 + 002333333333 목살 1.0
   └─ SET-260922-002  3.0kg   ← 002111111111 삼겹 2.0 + 002333333333 목살 1.0
          │ 주문 확정 → 출고
          └─ 거래명세서: "실속세트 › 국내산 삼겹살  002111111111  2.0kg"
```

**잠긴 설계 결정:**

1. **세트 상품 자체는 그냥 `products` 한 행이다.** 미니샵·발주·맞춤단가·명세서·PG가 코드 변경
   없이 그대로 돈다. "세트인가"는 `product_bundles` 행이 있느냐로 판단한다 — `products` 스키마는
   여전히 건드리지 않는다(1단계 설계 결정 3번 유지).
2. **세트 박스 한 개도 `inbound_scans` 한 행이다.** 재고 단위가 여전히 "박스 한 개"라 선입선출
   출고·출고 스캔·피킹 목록·라벨이 전부 기존 기계장치를 그대로 쓴다. 자체 세트번호
   (`SET-YYMMDD-NNN`)가 그 박스의 `trace_no` 자리에 들어간다 — 그래서 **출고 스캔에서 세트 박스를
   찍는 것도 코드 추가 없이 된다**(바코드 파서에 형식만 추가).
3. **세트 상품의 재고 단위는 kg이 아니라 "세트 1개"다.** 세트는 규격 상품이라 "1박스 45,000원"으로
   팔지 kg으로 팔지 않는다. 중량으로 세면 45,000원짜리 세트가 0.7세트만큼 팔릴 수 있다. 실제
   중량은 `bundle_assemblies.total_weight`에 따로 적어 라벨·명세서에 쓴다. 상품 수정 폼이 단위를
   kg으로 되돌리는 걸 **트리거로 막는다**(경로가 폼·일괄수정·관리자로 여럿이다).
4. **세트에 들어가는 고기는 반드시 "박스"에서 나온다.** 박스로 못 채우는 분량(기초재고 등 이력번호
   없는 재고)으로는 세트를 만들지 않고 `INSUFFICIENT_COMPONENT_BOXES`로 막는다. 이력번호 없는
   고기를 넣는 순간 역추적이 끊기고, **그게 이 기능의 존재 이유다.**
5. **유통기한이 지난 박스는 세트에 넣지 않는다.** 출고 차단(22단계)과 같은 논리다 — 재포장으로
   기한을 리셋하는 경로를 만들면 안 된다. 세트 박스의 기한은 **구성 박스 중 가장 이른 기한**을
   물려받는다.
6. **중첩 세트(세트를 구성품으로 하는 세트)는 금지**한다. 역추적이 재귀가 되면 명세서·라벨·단속
   대응 질의가 전부 복잡해진다. 1단계 전개만 지원한다.
7. **원장은 고쳐 쓰지 않는다.** 해체는 행 수정이 아니라 반대 부호 행(`BUNDLE_DISASSEMBLE` /
   `BUNDLE_RESTORE`) 추가다. 이미 출고된 세트는 해체할 수 없다(`PARTIALLY_SHIPPED`).
8. **입출고 기록이 있는 상품은 세트 상품으로 지정할 수 없다.** kg으로 쌓인 재고와 세트 개수가 한
   컬럼에서 뒤섞인다. 세트용 상품을 새로 만들라고 안내한다(화면에서 이름·판매가만 넣으면 상품까지
   한 번에 만들어준다 — 축종·원산지는 구성품에서 물려받고, 섞여 있으면 "혼합").

### 입고 실중량 검수 + 매입금액 자동 산정 (24단계)

현장 루틴을 끝까지 채웠다: **스캔 → 검증 → 측정(저울) → 확정(매입금액)**.

지금까지 중량 칸이 하나뿐이라 **바코드에 실려 온 표기중량과 저울에 찍힌 실중량이 같은 칸을 놓고
다퉜다.** 표기 20kg / 실측 19.8kg인 박스를 20kg으로 받으면 200g씩 돈을 더 주고, 재고도 200g씩
부풀어 출고에서 어긋난다. 이제 두 값을 따로 받아 차이를 기록하고, 매입금액을 실중량으로 산정한다.

```
002111111111 스캔
  → 표기중량 20.000kg (바코드 GS1-128 AI 3103에서 자동)
  → 실중량 19.800kg  (저울)
  → 차이 -0.200kg (-1.0%) · 허용 범위(±2%) 안
  → 매입 1,029,600원 (19.800kg × 52,000원, 상품 기본 매입단가 자동 적용)
```

**잠긴 설계 결정:**

1. **재고에 반영되는 건 언제나 실중량이다.** 표기중량(`labeled_weight`)은 대조용으로만 남긴다.
   기존 `weight`가 곧 실중량이라 원장·출고·정산 로직은 손대지 않았다.
2. **차이가 나도 입고를 막지 않는다.** 물건은 이미 창고에 들어와 있다(1단계와 같은 원칙). 허용
   오차(±2%)를 넘으면 화면에서 크게 알리고 집계에 남긴다 — 목적은 차단이 아니라 **어느 매입처가
   반복적으로 덜 보내는가**를 드러내는 것이다.
3. **매입금액은 실중량 기준**이다. 표기중량으로 청구받으면 그 차이가 그대로 손실이다.
4. **매입단가는 상품별 기본값 + 건별 스냅샷**이다. 스캔 시점의 단가가 박스에 복사되므로 나중에
   기본단가를 바꿔도 과거 매입금액은 흔들리지 않는다.
5. **매입금액은 계산 컬럼(`GENERATED`)이다.** 단가를 나중에 채워도 금액이 자동으로 따라오고,
   중량과 금액이 어긋난 행이 물리적으로 존재할 수 없다.
6. **금액은 원장(`stock_ledger`)에 넣지 않는다.** 원장은 수량의 진실이고 돈은 별개다. 섞으면 재고
   재계산이 금액 변경에 끌려다닌다.
7. **바코드에 중량이 있어도 바로 등록하지 않는다**(9단계에서 바꾼 동작을 되돌림). 그 값은 표기중량
   이고 기준은 저울이어야 한다. 대신 실중량 칸에 미리 채워 선택해두므로, 저울 값이 같으면 여전히
   Enter 한 번으로 끝난다.

**스키마** (`supabase/migrations/20260930000072_inbound_actual_weight_and_purchase.sql`)
- `inbound_scans.labeled_weight` · `purchase_unit_price` · `purchase_supplier`
- `inbound_scans.weight_variance` = `weight - labeled_weight` (GENERATED STORED)
- `inbound_scans.purchase_amount` = `ROUND(weight * purchase_unit_price, 0)` (GENERATED STORED)
- `product_purchase_prices` — 상품별 기본 매입단가. **원가라 바이어 분기를 아예 두지 않았다**
  (RLS에 고객 경로가 없다).
- `inbound_weight_tolerance()` = 0.02 — 화면(`lib/livestock/weight-variance.ts`)과 값을 맞춰야 한다.

**RPC**: `record_inbound_scan`(인자 3개 추가 — 22단계와 같은 방식으로 `record_inbound_scan_base`를
재사용하고 껍데기만 재생성, 이전 껍데기는 호출 모호성 때문에 DROP), `set_product_purchase_price`,
`update_inbound_purchase`(나중에 단가 채우기 + "이 상품 기본단가로"),
`list_inbound_purchases` / `summarize_inbound_purchases`.

**화면**
- **입고 스캔**: 표기중량 / **실중량(⚖️)** / 매입단가 / 매입처 네 칸. 단가·매입처는 한 차 분량이
  대체로 같아 스캔 후에도 비우지 않는다. 저장 전에 차이와 금액을 미리 보여준다.

  실측합계·차이·매입금액과 **단가 미입력 건수**(합계가 미완성이라는 신호), **오차 초과 건수와
  차액 금액**을 띄운다. "오차 초과만" 필터로 문제 매입처를 추린다. 원가 화면이라 manager 이상만
  수정할 수 있다(입고 자체는 staff도 하지만 단가는 관리 행위다).

### 수입 축산물 이력조회 API 조사 (26단계, 2026-09-23)

**계기**: 국내산 소·돼지·닭·오리·계란(25단계)은 실주소까지 확인됐으니, 남은 마지막 한 갈래인 수입육(②, `meatwatch.go.kr`)도 마저 찾아 연결해달라는 요청.

- data.go.kr이 이 항목을 왜 "LINK형"으로 분류했는지도 이걸로 설명된다 — 검역본부가 자기 시스템의 인증·과금(무료지만 심사)을 데이터포털에 위임하지 않고 직접 운영하기 때문으로 보인다.

### 미등록 묶음(공급자 자체 코드)을 특정 주문으로 바로 배정 (27단계, 2026-09-23)

**배경**: 정부 이력제·수입 이력 어디에도 없는 번호(공급자가 자체로 매긴 묶음번호 등)가 들어올 수 있다 — 예를 들어 고객이 미리 요청해서 받은 특수 부위. 이런 박스는 `EXCEPTION`(`NOT_FOUND`)으로 남고, 지금까지는 "입고 화면에서 상품 지정 → 주문이 confirmed 될 때까지 대기 → 출고 스캔 화면에서 그 박스를 다시 찾아 찍기"를 화면 세 개로 오가야 했다.

**구현**: 입고 화면에 **"주문에 바로 배정"** 버튼을 추가했다. `PENDING_MAPPING`/`EXCEPTION` 행에서 누르면 상품·주문 선택창이 펼쳐지고, 확정하면 새 RPC `resolve_inbound_mapping_to_order()`가 **기존 두 함수(`resolve_inbound_mapping` → `record_outbound_scan`)를 그대로 순서대로 호출**한다 — 새 재고 로직을 만들지 않고 한 트랜잭션으로 묶기만 했다. 중간에 실패하면(예: 그새 주문이 이미 다 채워짐) 상품 지정까지 전부 롤백돼 "상품은 지정됐는데 배정은 안 된" 반쪽 상태가 남지 않는다.

**잠긴 설계 결정:**
1. **대상 주문은 출고 스캔과 같은 기준(확정·배송중)이다.** 이 기능이 내부적으로 출고 스캔을 그대로 부르기 때문에 접수대기 주문을 골라봐야 `ORDER_NOT_SHIPPABLE`로 막힌다 — 그래서 목록 자체를 출고 스캔 화면(`app/dashboard/outbound/page.tsx`)과 동일한 쿼리로 좁혀뒀다.
2. **박스 무게가 주문 필요량보다 많아도 된다.** `record_outbound_scan`에 무게를 안 넘기면(NULL) 알아서 "박스 잔량과 주문 필요량 중 작은 쪽"만 가져가고 나머지는 그 상품의 일반 재고로 남는다 — 굳이 정확히 맞춰 받을 필요가 없다.
3. **기존 두 화면(입고 예외 처리, 출고 스캔)은 그대로 둔다.** 이건 그 둘을 대체하는 게 아니라 지름길 하나 추가한 것이다 — 평소처럼 상품만 지정하고 나중에 출고 스캔에서 처리하는 경로도 그대로 쓸 수 있다.

**DB**: `supabase/migrations/20260930000074_resolve_inbound_to_order.sql` — `resolve_inbound_mapping_to_order(p_scan_id, p_product_id, p_order_id, p_remember)`.

**미검증**: 로컬 Postgres 스택 없이 코드로만 작성 — `resolve_inbound_mapping`과 `record_outbound_scan`은 각각 이미 DB 테스트를 통과한 함수라 조합 자체의 위험은 낮다고 보지만, 실제 DB에 적용 후 실계정으로 왕복 확인 필요.

### 박스 나눠서 입고 — 공급자가 여러 상품을 한 코드로 묶어 보낸 경우 (28단계, 2026-09-23)

**배경**: 도매업체가 주문한 서로 다른 상품 여러 개를, 공급자가 배송 편의상 박스 하나·코드 하나로 묶어 보내는 경우가 있다. 개별 포장에 각자 이력번호가 붙어 있으면 그냥 하나씩 스캔하면 되지만(기존 기능 그대로), **코드가 딱 하나뿐이고 그 안에 실제로는 다른 상품이 섞여 있는 경우**는 지금까지 대응이 없었다.

**설계 판단 — 이건 프론트 전용 기능이다, 백엔드가 자동으로 알 방법이 없다.** "이 코드 하나가 사실 A 3kg + B 2kg이다"는 코드 자체에는 담겨 있지 않다(GS1 표준에도 그런 다중 품목 표현이 없다) — 박스를 직접 열어본 사람만 아는 정보다. 그래서 백엔드에는 새 개념을 추가하지 않았다: `inbound_scans`는 애초에 `trace_no`에 UNIQUE 제약이 없다(1단계 설계 결정 1번 — "재고의 단위는 이력번호가 아니라 박스 한 개"), 즉 **같은 코드로 여러 번, 상품을 다르게 지정해서 스캔하면 그대로 여러 박스 행으로 쌓이는 게 원래 지원되던 동작**이었다. `record_inbound_scan_base`도 `p_product_id`를 명시하면 그 상품으로 바로 확정한다(자동매칭을 건너뜀). 즉 **DB·RPC는 그대로**이고, 프론트에서 "같은 코드 + 여러 (상품, 무게) 쌍"을 반복 제출하는 UI만 추가했다.

**구현**: 입고 화면에 **"박스 나눠서 입고"** 토글을 추가했다. 켜면 코드 입력칸 하나 + (상품, 무게) 행을 여러 개 추가할 수 있는 패널이 뜬다. "전체 입고"를 누르면 같은 코드로 `recordScanAction`을 행 개수만큼 반복 호출한다 — 각 호출에 상품을 명시적으로 지정해서 보내므로 `NORMAL`로 바로 확정되고, 이력 확인/매핑 대기 단계를 거치지 않는다.

**잠긴 설계 결정**:
1. 상품이 2개 미만이면 막는다 — 하나만 넣을 거면 원래 입력창을 쓰면 된다.
2. 중복 스캔 경고(`confirmDuplicate`)를 항상 켜서 보낸다 — 이 흐름 자체가 "같은 코드를 여러 번 찍겠다"는 의도적 행위라, 매번 확인창이 뜨면 오히려 방해된다.
3. 한 행이 실패하면(예: 상품이 삭제됨) 그 자리에서 멈추고 에러를 보여준다 — 이미 성공한 앞의 행들은 롤백하지 않는다(각 호출이 독립 트랜잭션이라 원천적으로 전부 롤백은 불가능하고, 실패한 상품만 다시 채워 넣으면 되므로 문제가 되지 않는다).

**미검증**: 코드 작성만 하고 실제로 눌러보지 않았다. `recordScanAction`을 반복 호출하는 구조라 개별 호출 자체는 기존에 검증된 경로지만, 화면 흐름은 확인 필요.

### 개발용 샘플 미리보기 (2026-09-23)

사장님이 화면 구성을 검토하는 용도로, 입고 화면에 이력번호 4가지 유형(①일반 개체 ②정부 발행 묶음 ③공급자 자체 묶음 ④고객주문용 공급자 묶음)을 버튼 하나씩으로 목록에 띄워보는 패널을 추가했다.

**잠긴 결정: 실제 API·DB는 전혀 건드리지 않는다.** `master_livestock`이 업체 구분 없는 플랫폼 공용 캐시라, 검토용 가짜 데이터를 거기 심으면 나중에 실제 서비스 데이터와 섞일 위험이 있다고 판단해 순수 프론트 상태(`rows`)에만 미리보기 행을 얹는 방식으로 만들었다. 새로고침하면 사라지고, 행마다 개별 삭제 버튼과 "샘플 전체 지우기"를 뒀다. `isSample` 행은 상품 지정·주문 배정 등 실제 동작 버튼을 전부 숨긴다(눌러도 아무 일도 안 나는 걸 방지).

**상품관리 화면(`/dashboard/products`)에도 같은 패턴으로 추가했다.** 입고가 확정되면 재고가 어디에 어떻게 보이는지(재고 수량 + 신선도 표시) 4가지 유형별로 미리 볼 수 있다. `ProductTable`에 `sampleProducts`/`sampleStockSummaries` 로컬 상태를 얹고 실제 `products`/`stockSummaries`와 합쳐서(`allProducts`/`allStockSummaries`) 렌더링한다 — DB 쿼리는 그대로다. `run()`(모든 실제 변경 액션의 공통 관문)에 샘플 id 가드를 추가해 수정/보관/삭제/재고조정을 전부 막고, 대신 "샘플 삭제" 버튼(로컬 상태에서만 제거)을 별도로 뒀다.

**샘플 3·4번(공급자 자체 묶음)은 도축일·등급이 끝까지 비어 있다.** 정부 API에 한 번도 안 걸린 코드라 `master_livestock`이 채워진 적이 없기 때문이다 — 재고 수량은 정상 반영되지만 신선도 칸은 "박스 N개"만 뜨고 도축일/등급은 안 보인다. 1·2번(API 확인됨)은 도축일·등급까지 정상 표시된다. 이 차이 자체가 사용자에게 실제로 의미 있는 정보라 샘플에도 그대로 반영했다.

**남는 것**: 그때까지는 수입육 이력번호를 찍어도 `EXCEPTION`(`API_ERROR` 또는 키 미설정)으로만 쌓인다 — 입고 자체는 막히지 않으므로 현장 업무에는 지장 없다.

## 29단계 — 공급처 원본 명세서 → 미확정 입고 (A: 받아들이기)

상위 공급처(도축장·대형유통사)가 납품과 함께 주는 거래명세서/납품명세서를 원본 그대로 받아 플랫폼 양식에 맞춰 넣고, **부족한 항목을 공급사가 한눈에 보게** 하는 기능. 기존 "엑셀 대량 입고"(13단계)와 다르다 — 그건 우리가 정한 형식(이력번호+중량)만 받아 **즉시 입고를 실행**하는 큐고, 이건 **남의 형식 문서를 증빙으로 보관하고 대조 대상으로 대기**시킨다.

### 플랫폼의 역할 범위 (사장님 지침, 2026-09-23)

> 플랫폼은 도소매 연결 폐쇄형이다. 도매 이후부턴 플랫폼이 리드하지만 **공급사 이전 공급처와의 관계는 플랫폼이 못 건드린다.** 기존 걸 받아서 플랫폼 양식에 맞춘다 정도다. 플랫폼 기준은 법적 규제와 범용 상품관리에 맞춘 것이니 **최대한 그 기준에 맞춰 넣고, 미흡한 건 도매가 공급처에서 받아 채우게** 해야 한다. **플랫폼은 문서의 미흡함을 공급사가 쉽게 알 수 있도록 해주면 된다.**

여기서 나오는 두 가지 금지사항:
- 공급처에 뭔가를 요구하거나 양식을 강제하는 기능을 만들지 않는다. 대신 **공급사가 공급처에 보낼 요청 문구를 만들어 준다**(요청 항목만 추려 복사).
- **순서를 가정하지 않는다.** 명세서가 먼저 올 수도, 창고 스캔이 먼저일 수도 있다. "들어올 예정" 같은 이름은 명세서 우선을 전제하므로 쓰지 않는다.

### 잠긴 설계 결정

**1. 서류만으로는 재고가 잡히지 않는다.** 재고는 박스 스캔만이 만든다(설계 결정 1·2번 유지). 서류로 재고를 만들면 ① 실물 없는 고기가 미니샵에 떠서 식당이 주문할 수 있고 ② 이력번호가 빈 채 재고가 생겨 나중에 거래명세서에 이력을 못 찍는다. 이 마이그레이션은 `stock_ledger`/`products.stock_quantity`를 일절 건드리지 않는다.

**2. 서류의 중량은 플랫폼의 표기중량(`labeled_weight`)이다.** 공급처가 주장하는 값이고, 창고 저울로 잰 실중량과 대조할 대상이다. 24단계가 이미 표기중량 vs 실중량 ±2% 구조를 갖고 있어 새 개념을 만들지 않고 같은 이름에 꽂는다. **실중량으로 오해하면 매입금액이 통째로 틀어진다.**

**3. 형식은 미리 알 수 없으므로 공급처별로 학습한다.** `trace_product_map`이 "부위→상품"을 한 번 묻고 학습하듯, 칸 위치를 한 번 받아 `supplier_document_formats`에 저장하고 같은 공급처 서류는 다음부터 그대로 읽는다. 덕분에 **실물 샘플을 미리 모을 필요가 없다** — 실제 서류가 도착하는 그 순간 배운다.

**4. 자동 인식은 초안까지만.** 틀리게 읽은 값이 그대로 매입금액이 되면 안 되므로, 사람이 표에서 확인·수정한 뒤에야 저장된다.

**5. 못 읽는 서류는 원본 보관만 한다.** 사진과 스캔본 PDF는 글자 정보가 없다. 입고 화면에서 손으로 받아적게 만들지 않는다 — 현장 화면은 바코드 찍는 데 집중해야 한다. 품목 줄이 0개인 문서도 저장된다(`status = DRAFT`).

**6. 기록 삭제는 기본이 "감추기"다.** 축산물이력법상 매입 기록은 1년, 매출은 2년 보관해야 한다. 공급처 명세서는 매입 증빙이므로 목록의 기본 동작은 취소 처리(`DISCARDED`)이고 원본은 남는다. 완전 삭제는 취소 처리된 것만 가능하다. 기록이 있는 상품을 삭제 대신 '보관'으로 감추게 한 12단계와 같은 판단.

### 플랫폼 표준 — 서류에서 받아야 하는 것 (사장님 확정 2026-09-23)

업체 유치 전 "표준을 만들어가는 단계"에서 확정했다.

| 항목 | 수준 | 채우는 주체 |
|---|---|---|
| 공급처 이름 | 필수 | 공급사가 입력 |
| 서류 날짜 | 권장 | 공급사가 입력 |
| 명세서 번호 / 합계 금액 | 선택 | 서류에 있으면 (합계는 검산용) |
| 품목명 | 필수 | 공급처 |
| 내 상품 연결 | 필수 | 공급사가 화면에서 선택 |
| 표기중량 | 필수 | 공급처 |
| 단가 **또는** 금액 | 필수 | 공급처 (하나만 있으면 나머지는 중량으로 계산) |
| 이력번호 | 권장 | 창고 스캔이 채움 |
| 등급 | 선택 | 공급처 (이력번호 있으면 공공조회 값 우선) |
| 수량(박스 수) | 선택 | 공급처 |

판정 근거:
- **이력번호를 필수로 올리지 않은 이유**: 창고에서 박스를 찍으면 채워지므로 서류에 없어도 최종 기록은 완성된다. 다만 축산물이력법상 거래내역에 이력번호가 남아야 하므로 **안내 문구에 법적 근거를 담아** 공급사가 공급처에 요구할 때 쓰게 했다.
- **등급이 선택인 이유**: 이력번호가 있으면 공공 이력조회가 채워주고 그 값이 우선이다. 다만 **이력번호도 등급도 없으면 품질을 확인할 방법이 아예 없어** 그 경우에만 짚는다(`GRADE_UNKNOWN`, 권장).
- **단가·금액이 필수인 이유**: 매입 정산의 근거다. 둘 중 하나만 있어도 중량으로 나머지를 계산할 수 있어 "둘 다 없을 때"만 필수 누락으로 본다.

미흡 항목은 **채울 주체를 셋으로 갈라** 보여준다 — `FROM_SUPPLIER`(공급처에 요청), `FROM_STAFF`(공급사가 화면에서), `FROM_SCAN`(찍으면 채워짐). 공급처에 요청할 것만 추린 문구 복사 버튼이 붙는다.

### PDF에서 표를 되살리는 법 (중요)

**글자만 뽑으면 칸 경계가 사라진다.** 실제로 확인한 결과:

```
한우 등심 1++ 002191840078 8.20 52,000 426,400
```

띄어쓰기로 자르면 품목명이 세 조각 나고 천단위 쉼표와 엉킨다. 더 나쁜 건 **칸이 빈 줄**이다 — 이력번호가 없으면 뒤가 전부 한 칸씩 밀려 **중량 자리에 단가가 들어간다.** 매입금액이 통째로 틀어지는 사고다.

그래서 `lib/livestock/pdf-extract.ts`가 글자마다 좌표(x, y)를 함께 읽어 세로줄을 복원한다. 빈 칸은 그 x 구간에 글자가 없다는 사실로 드러나 빈 칸인 채 남는다. **세로줄 기준은 조각 3개 이상인 "표처럼 생긴 줄"에서만 잡는다** — 제목·주소 줄까지 넣으면 엉뚱한 칸이 생긴다. 글자가 없는 PDF(스캔본)는 빈 결과가 나오고, 그건 실패가 아니라 "읽을 수 없는 문서"라는 판정이라 보관 경로로 넘어간다.

같은 작업에서 별개 버그도 찾았다 — `applyColumnMap`이 **헤더 줄 위쪽**을 품목으로 넣고 있었다. CSV는 헤더가 첫 줄이라 안 드러났는데, PDF는 제목·공급처 줄이 위에 있어 첫 품목이 통째로 밀렸다.

### 테이블 (`supabase/migrations/20260930000075_inbound_documents.sql`)

| 테이블 | 역할 |
|---|---|
| `inbound_documents` | 올린 명세서 1장. `status`: DRAFT(원본만) / PENDING(대조 대기) / CLOSED / DISCARDED |
| `inbound_document_lines` | 명세서의 품목 1줄. `trace_no`·`grade` 모두 nullable |
| `supplier_document_formats` | 공급처별 칸 위치 학습 (`column_map jsonb`) |
| Storage `inbound-documents` | 비공개 버킷. 경로 `<wholesaler_id>/<document_id>/<파일명>` |

재고에 영향이 없으므로 쓰기를 RPC로 강제하지 않고 RLS 직접 쓰기를 허용한다 — `inbound_import_jobs`와 같은 예외 사유(설계 결정 6번).

`can_access_wholesaler_folder()`는 Storage 경로 첫 칸을 UUID로 캐스팅하되 **실패를 예외로 잡아 거부**한다. 정책 안에서 그냥 `::uuid`를 쓰면 경로가 UUID가 아닐 때 에러가 나서 조회 자체가 터진다.

### 검증 상태

## 보안 점검 — 권한 게이트 NULL 비교 버그 (2026-09-24)

입고쪽 보안·로직 점검에서 나온 결과. 입고 흐름 자체(스캔 → 원장 → 재고, 역분개 취소, 명세서는 재고를 안 만듦, 스토리지 폴더 정책, 원장 테이블 SELECT-only RLS)는 설계대로 잠겨 있었다. 구멍은 **권한 검사 식이 NULL이 되는 경우**에 몰려 있었다.

### 원인

SECURITY DEFINER RPC 여러 개가 아래 두 패턴으로 검사했다.

```
(a) IF v_row.wholesaler_id <> v_wholesaler_id THEN RAISE ...
(b) IF v_wholesaler_id <> get_current_wholesaler_id()
       AND NOT is_org_staff_of_wholesaler(v_wholesaler_id, owner/manager) THEN RAISE 'FORBIDDEN'
```

비교 대상이 NULL이면 결과가 NULL이고, plpgsql의 `IF`는 NULL을 거짓으로 본다(3치 논리). 실제로 NULL이 되는 계정이 흔하다.

| 계정 | NULL이 되는 값 | 뚫리던 것 |
|---|---|---|
| 고객(식당) | `resolve_current_wholesaler_id()` | (a) 통과 → 연결된 어느 공급사 상품이든 `adjust_product_stock`(재고 조정)·`set_product_archived`(보관). 상품 ID는 미니샵·주문내역에 노출된다. 고객–공급사가 N:N이라 범위는 "연결된 모든 공급사". |
| 초대 직원(staff) | `get_current_wholesaler_id()` (원 가입자만 인식) | (b) 통과 → owner/manager 전용이어야 할 매입단가·판매가 일괄수정·재고조정·보관·네고 단가 확정. 화면은 `requireOrgRole`로 막지만 anon 키가 공개라 RPC 직접 호출은 못 막는다. |

라이브 DB 조회(`pg_get_functiondef ~ 'v_wholesaler_id IS NULL'`)로 `adjust_product_stock`, `set_product_archived`, `delete_product_bundle`, `disassemble_bundle_assembly`가 가드 없이 배포돼 있음을 사장님이 확인했다(2026-09-24).

### 수정 (`supabase/migrations/20260930000097_null_safe_tenant_gates.sql`)

### 점검 2 — 선입선출 차감 + 세트(BOM) 역추적 무결성 (`supabase/migrations/20260930000100_fifo_expired_boxes_and_bundle_guards.sql`)

세트 역추적의 뼈대(원본 이력번호 스냅샷, RESTRICT 외래키, 중첩 금지, 해체는 역분개, 부분 출고된 세트 해체 차단, 원본 박스 소실 시 안전 정지, 세트번호 advisory lock, 동시 제작은 부족 시 통째로 롤백)는 설계대로였다. 무게·수량 컬럼은 전부 `NUMERIC(10,3)`으로 통일돼 있음을 실제 DB에서 확인했다(법 규제가 아니라 GS1-128 AI 3103이 g 단위라는 068의 결정).

| # | 문제 | 처리 |
|---|---|---|
| 1 | 확정 자동배정(`apply_order_shipment`)에 유통기한 조건이 없었다. 출고 스캔(거부)·세트 제작(제외)과 달리 기한 지난 박스를 가장 오래됐다는 이유로 1순위로 잡았고, 스캔 없이 운송장으로 바로 배송되면 그 박스가 명세서에 찍혔다 | 자동배정 대상을 "기한 안 지난 NORMAL 박스"로. **가용량 = 쓸 수 있는 박스 잔량 + 박스 없는 재고(원장 합계 − 전체 박스 잔량)** — 원장 합계로만 보면 기한 지난 박스 무게가 '이력 미추적 분량'으로 몰래 빠진다. 잠금 아래 2차 확인도 박스 없는 재고 기준. 기한 지난 박스는 재고 숫자에는 남는다(폐기는 재고조정으로 사람이) |
| 2 | 기존 상품을 세트로 지정할 때 "입출고 기록 없음"만 보고 수동 재고(`stock_quantity`)는 안 봤다. 상품 폼 기본값이 10이라 첫 제작 때 기초재고로 편입돼 **박스 없는 세트 10개**(이력번호 없음)가 생겼다 | `save_product_bundle`이 수동 재고 ≠ 0이면 `PRODUCT_HAS_MANUAL_STOCK` — 화면 문구: 재고를 0으로 맞춘 뒤 지정 |
| 3 | 세트 제작이 보관(archived) 처리된 구성품의 박스를 그대로 썼다 | `assemble_product_bundle` 첫머리에서 `COMPONENT_ARCHIVED` |
| 4 | 같은 트랜잭션에서 만든 세트들은 `created_at`이 같아 선입선출 순서가 임의였다 | `ORDER BY created_at, trace_no` — 세트는 `SET-YYMMDD-NNN` 순 = 제작 순 |

안 고친 것(낮음, 화면 작업): 명세서에서 박스 없이 빠진 분량(기초재고 등)은 이력번호 목록에 아무 표시가 없다 — "이력 미추적 Xkg" 한 줄을 넣어주면 공급사가 빠진 걸 알 수 있다.
