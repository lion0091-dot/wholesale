# 검증 규칙 (배포 전 점검 방식)

2026-09-26 밤 세션에서 실제로 돌려 본 방식을 규칙으로 고정한다. 이유: 단위·통합 테스트가 통과해도 규모(성능)·안내 흐름(따라가기)·기능 사이 상호작용 문제가 배포 뒤에 나왔다. 테스트는 만든 사람의 가정만 검사한다.

## 1. 기본 관문 (배포 전 전부 통과)

1. `npx tsc --noEmit`
2. `npx vitest run` (단위)
3. `npx vitest run --config vitest.integration.config.mts` (통합, 로컬 Docker Supabase 필요)
4. `npm run build` — 타입체크만으로는 "use server" export 오류 등을 못 잡는다.

하나라도 실패하면 원인을 **테스트 오류인지 실제 버그인지 구분해서** 보고한다. 테스트를 통과시키려고 기대값을 바꾸기 전에 왜 다른지 먼저 확인한다.

## 2. 찐오류 점검

- 변경분 diff(`git diff <기준커밋> HEAD`)를 읽고 **재현되는 것만** 오류로 적는다. 취향·가설·"~일 수 있음"은 오류가 아니다.
- 각 오류에는 재현 근거(입력→잘못된 출력, 또는 측정 수치)를 붙인다. 재현 못 하면 "확인하지 못했다"고 쓴다.
- 확인했지만 오류가 아니었던 것도 한 줄로 남긴다(같은 의심을 반복하지 않게).

## 3. 규모(부하) 점검

대상: 화면을 열 때마다, 또는 주기적으로(종 배지 30초 등) 부르는 DB 함수·쿼리, 그리고 "여러 번호를 한꺼번에 다루는" 조회.

- 실제 규모로 시간을 잰다: 전표 줄 5,000~10,000개, 박스 1,500~3,000개 기준. 트랜잭션 안에서 시드하고 `ROLLBACK`한다.
- **두 가지를 다 잰다**: ① `ANALYZE` 전(통계 없음) ② `ANALYZE` 후. 그리고 RLS가 적용되는 역할(authenticated)과 SECURITY DEFINER 실행 시(RLS 우회) 계획이 다를 수 있으니 실행 계획을 함수 본문 그대로 따로 본다.
- 기준: 화면 로드·주기 호출 함수는 실측 100ms 안팎 목표, 상한 1.5초. 넘으면 배포하지 않는다.
- 흔한 원인: 박스(번호)마다 전체 줄을 훑는 함수 호출(`document_lines_matching_trace`를 행마다 부르기), `upper()`로 감싸 인덱스를 못 쓰는 조건, CTE가 행마다 재계산됨(→ `AS MATERIALIZED`), OR 조건이라 인덱스 못 씀(→ 열마다 조인 후 UNION).
- **함수를 다시 짜면 옛 함수와 결과를 양방향 `EXCEPT`로 비교한다**(옛 본문을 다른 이름으로 복사해 같은 데이터에 돌림). 로트↔개체 구성원 같은 우회 규칙 데이터도 같이 심는다. 비교 SQL에서 `\i`는 컨테이너 밖 파일을 못 읽으니 내용을 직접 붙인다.
- 새 성능 가드를 추가하면 **옛 느린 버전으로 되돌려 실제로 실패하는지 한 번 확인**한다.
- 가드 위치: `tests/integration/perf-guard.itest.ts`. 주기 호출 함수를 새로 만들면 여기에 넣는다.

## 4. 따라가기(안내 흐름) 점검

기준은 "업무를 몰라도 안내만 따라가면 끝까지 끊김 없이 간다"이다.

- 새 안내 카드·오류·버튼은 **글자 안내로 끝내지 않고** 행동 지점(그 칸, 그 화면)까지 데려가는지 본다. 누를 수 없는 "기다림" 버튼에는 반드시 탈출구(마감하기 등)를 함께 둔다.
- 안내 순서가 실제 필수 단계를 빠뜨리지 않는지 본다(예: 전표번호 필수인데 카드가 곧바로 "저장"을 가리킴).
- 카드가 가질 수 있는 상태가 늘면 `lib/livestock/inbound-next-step.matrix.test.ts`의 조합에 넣는다. 큰 버튼을 바꿀 때는 원래 있던 작은 링크가 사라지지 않았는지 이 표가 잡는다.
- 화면을 눈으로 본 것이 아니면(카카오 로그인 필요) 그렇게 밝힌다. 서버 액션·코드 수준 확인과 실화면 확인을 구분해서 보고한다.

## 5. 실제 파일 시험

- 공급처 전표 양식은 실제 파일로 돌린다: `docs/test-samples/`(샘플 6개 + `00-시험표.xlsx`), 재생성은 `node scripts/build-test-samples.mjs`.
- 자동 시험: `tests/integration/sample-documents.itest.ts`가 샘플을 읽어 저장→스캔→대조→자동 마감까지 돌린다. 파서·매칭 규칙을 바꾸면 여기에 사례를 추가한다.
- 실계정 시험(사장님)은 시험표 순서대로: 사무실 PC에서 전표 올리기 → 폰에서 입고 스캔 → PC에서 카드·마감 확인.

## 6. 배포 순서 (사장님이 "배포"라고 할 때만)

1. 라이브 DB 마이그레이션 적용(`npx supabase db query --file <파일> --linked`) — 적용 뒤 함수 본문·컬럼으로 **실제 반영 확인**.
2. 커밋(메시지는 파일로 써서 `git commit -F`).
3. push.
4. 메모리에 상태 기록.

DB를 안 바꾼 변경은 1을 건너뛴다. 사용자 요청 범위 밖의 라이브 쓰기는 하지 않는다.

## 7. 보고 형식

- 통과 수(단위/통합), 타입체크, 빌드 결과.
- 부하 수치(전/후 표).
- 찐오류와 따라가기 끊김을 나눠서, 고친 것·못 고친 것·확인 못 한 것을 분명히.
- 확인하지 못한 것은 "확인 안 했다"고 쓴다(실계정 화면, Vercel 성공 여부 등).
