> **2026-09-28 개정 (마이그레이션 140) — 소의 기준에 "품종"(한우·육우·젖소)을 추가했다.** 소 = 축종 + **품종** + 부위 + 등급 + 원산지. 한우와 육우는 같은 부위·등급·국내산이라도 값·표시 의무가 달라 별개 상품이다(육우도 국내 도축이면 원산지가 국내산이라 원산지로는 안 갈린다).

> **2026-09-27 개정 (마이그레이션 137) — 아래 114·손 등록 차단 내용은 이 개정으로 대체됐다.**

> - 이력번호 출처 키(`products.trace_key`, 돼지 농장·닭/오리 도축장)와 `trace_identity_key()`는 **삭제**했다 — 발주 전에는 알 수 없는 값이라 미리 등록이 불가능했다. 농장·도축장은 박스 기록으로만 남는다.
> - **손 등록 잠금 해제**(`traceable-categories.ts` 삭제): 소·돼지·닭·오리·계란도 상품 관리에서 미리 등록할 수 있다. 같은 키는 앱 검사가 거부하고 DB 유니크 인덱스(`idx_products_cattle/pork/poultry_egg_identity`)가 마지막으로 막는다. 입고 스캔 자동 생성은 같은 키 상품이 있으면(미리 등록한 것 포함) 새로 만들지 않고 그 상품에 붙는다.
> - 키 축종의 원산지는 `lib/products/origin-options.ts` 목록(국내산·미국산·호주산·뉴질랜드산·캐나다산·브라질산·스페인산·기타 수입산)에서만 받는다(신규 등록·발주서). 상품명은 소 "부위 등급", 돼지 "부위", 닭·오리·계란은 축종 이름.
> - "기본 납품 품목 불러오기" 시드는 키가 없는 축종(양·가공육)만 남긴다.
> - **알고 있어야 할 것:** ① 이력조회가 주는 수입 원산지(`trace_origin`)는 API의 국가명 그대로("미국")라 목록의 "미국산"과 글자가 다르다 — 사장님 결정("원산지는 like로")으로 상품·스캔 매칭은 `origin_matches()`(한쪽이 다른 쪽을 포함하면 같음, 137)를 쓴다. 상품·발주서 사이 원산지 비교도 같은 방식으로 한다. ② 라이브 적용 전이며, 적용 시 옛 "닭/오리" 행이 있으면 마이그레이션이 중단된다(라이브는 소 상품 1건뿐임을 2026-09-27 확인).


같은 키의 상품은 같은 상품이다 → 중복 등록을 막고, 등록 후 키 항목을 잠근다. 공공 이력 체계가 축종마다 달라서 키도 축종마다 다르다.

| 축종 | 키 | 상태 |
|---|---|---|
| 소 | 축종 + 부위 + 등급 + 원산지 | **구현됨** |
| 돼지·닭·오리·계란 | **이력번호에서 파싱한 출처 + 명세서(이력)의 부위** — 돼지 농장, 닭·오리 도축장(축종코드로 구분), 계란 발급월일+업체 | **구현됨(자동 생성 경로만)**, 사장님 "일단" 결정 |
| 양·기타 | 미정 | 결정 대기 |

**상품명은 키가 아니라 표시 이름이다.** 축종은 화면에서 `[소]` 태그로 자동으로 앞에 붙으므로(`lib/products/display-name.ts`), 소 상품명은 **"부위 + 등급"**으로만 저장한다(`등심 1++` → 화면 `[소] 등심 1++`). 부위가 비면 끝에 `(부위 미지정)`.

## 구현

- **키 정의 한 곳:** `lib/products/identity-key.ts` — `identityFieldsFor(축종)`, `composeIdentityName(...)`. 새 축종은 표에 한 줄 추가하면 된다.
- **등록** (`createProductAction`): 소는 부위·등급·원산지 필수, 이름은 서버가 조합(폼에서 온 이름은 무시), 같은 키가 이미 있으면 거부. 보관된 같은 상품이 있으면 "복원해서 쓰세요"로 안내. 중복 검사는 공급사 안에서만.
- **수정** (`updateProductAction`): 소는 부위·등급·원산지·이름이 등록 후 잠긴다. **비어 있던 부위·등급 칸만 한 번 채울 수 있고**(이력으로 자동 생성된 "(부위 미지정)" 상품에 부위 채우기) 채우면 이름이 다시 만들어지며 키 중복도 검사한다. 신규 등록과 달리 수정에서는 부위·등급을 요구하지 않는다(가격만 고치는 경우).
- **폼** (`product-form-view.tsx`): 소를 고르면 상품명 칸이 자동 조합 미리보기(읽기 전용)가 되고 부위·등급이 필수. 등록 후 값이 있는 부위·등급은 잠금 표시.
- **입고 자동 생성 (마이그레이션 113):**
  - 기존 상품을 찾을 때 소는 **원산지까지** 본다. 이름은 `부위 등급`. 이력에 등급이 없으면 **명세서 줄에서 딱 하나로 좁혀지는 등급**으로 채운다(`lookup_document_grade`, 사장님: "기반은 명세서"). **이력이 주는 값이 항상 우선**, 명세서는 빈칸만 메운다(부위와 같은 원칙).
  - `record_inbound_scan_base`의 **학습된 매핑**(`trace_product_map`, 원산지 없음) 조회도 소는 원산지가 같은 상품만 후보로 삼는다 — 안 그러면 수입 소 이력이 국내산 상품에 조용히 붙는다(통합테스트로 발견).
  - 원산지 판정은 `trace_origin(trace_kind, origin_country)` 한 함수. TS 쪽 기준은 `resolveTraceOrigin()`(`lib/livestock/inbound-requirements.ts`) — **바꾸면 양쪽을 같이 고칠 것**(원산지 표기는 법적 문제).
- **소 외 축종 (마이그레이션 114):** `products.trace_key`(새 컬럼) + `trace_identity_key()`(DB) ↔ `traceIdentityKey()`(`lib/livestock/trace-number.ts`) — 돼지 `돼지:<농장6>`, 닭 `닭:<도축장3>`, 오리 `오리:<도축장3>`, 계란 `계란:<월일4>-<업체3>`. 입고 자동 생성이 **(카테고리, trace_key, 부위)**가 같은 상품을 찾아 재사용하고 없으면 만든다 — 일련번호가 달라도 같은 농장+같은 부위면 같은 상품, 같은 농장이어도 부위가 다르거나 농장이 다르면 다른 상품, 닭과 오리는 도축장이 같아도 다른 상품. 부위는 이력조회가 주면 그것, 아니면 **명세서 줄**(기반은 명세서), 둘 다 없으면 "(부위 미지정)"이 출처별로 하나. 등급·원산지는 이 규칙의 키가 아니다. 이름은 출처가 다른 같은 부위 상품이 구분되게 `삼겹살 (농장 400770)`, 닭/오리는 `닭 훈제 (도축장 777)`. DB 유니크 인덱스 `idx_products_trace_key_identity`(새 컬럼이라 기존 중복 없음)가 동시 생성도 막고 자동 생성 함수가 위반 시 먼저 생긴 상품을 쓴다. 스캔 기록의 학습된 매핑(`trace_product_map`)도 출처 키가 다른 상품으론 안 새게 거른다.
  - **범위 밖(알고 있어야 할 것):** ① 수동 등록(상품 폼)은 이력번호가 없어 이 규칙의 중복 검사 대상이 아니다 — 돼지·닭·오리 수동 등록은 여전히 중복 가능. ② 자동 생성은 공공 이력 캐시(master_livestock) 행이 있어야 돈다 — 조회 결과가 없는 번호(예: 결과 0건이던 오리 번호)는 EXCEPTION으로 남고 상품이 안 만들어진다. ③ 카테고리 "닭/오리" 한 덩어리·계란 카테고리 없음(계란은 축종을 몰라 자동 생성 안 됨). ④ 이 규칙의 "출처 = 상품" 모델은 사장님 결정 — 같은 농장·같은 부위의 물건은 한 상품이라 등급이 달라도 합쳐진다.
- **소 DB 유니크 (마이그레이션 121, 2026-09-26 라이브 적용):** `idx_products_cattle_identity` = (공급사, 부위, 등급, 원산지) 유니크, `WHERE category='소'`(보관 상품 포함). 처음(121)엔 세트 상품 때문에 "단위가 세트면 제외" 조건이 있었으나 세트 개념을 제거하면서(122) 뺐다. 입고 자동 생성 함수는 동시 생성 충돌 시 소도 먼저 생긴 상품을 찾아 쓴다(예전엔 소는 `PRODUCT_NOT_FOUND`로 실패). 검증: `scripts/db-test-cattle-identity-unique.sql`(5건), `scripts/db-test-cattle-identity-concurrency.sh`(세션 2개 동시 생성). 통합 테스트 하네스는 소 상품에 등급을 자동으로 다르게 붙인다(같은 키 시드가 막히므로).
- **이력 대상 축종은 손 등록 차단 (2026-09-26, 사장님 결정):** 소·돼지·닭/오리 상품은 입고 스캔으로만 만들어진다(`lib/products/traceable-categories.ts`). `createProductAction`이 이 축종을 거부하고, 신규 등록 폼은 그 카테고리를 고를 수 없으며, "기본 납품 품목 불러오기"도 이력 대상 품목은 뺀 것(`MANUAL_DEFAULT_DELIVERY_ITEMS`)만 만든다. 양·가공육처럼 이력번호가 없는 품목만 손으로 등록한다. 수정 화면·이미 있는 상품은 그대로. 이력번호 없는 상품이 스캔 자동 생성 상품과 따로 생겨 중복되는 길이 닫힌다 — 돼지·닭/오리의 "직접 등록 중복" 결정 대기도 이걸로 해소됐다. 로그인·온보딩·첫 화면의 "상품 등록" 홍보 문구는 손대지 않았다.
- **하지 않은 것:** 기존 소 상품의 이름 일괄 변경(새 등록부터 적용), 돼지·닭·오리 규칙(수동 등록 상품 기준).

## 이력번호 12자리 구조 (사장님 제공 표)

첫 자리가 축종코드: **소 0 · 돼지 1 · 닭 2 · 계란 3 · 오리 5**.
돼지 = 코드1 + 농장식별 6 + 일련 5 (실제 번호 `140077000150`의 농장 `400770`이 API의 `farmUniqueNo`와 일치 확인) · 닭·오리 = 코드1 + 도축장 3 + 일련 8 · 계란 = 코드1 + 발급월일 4 + 표시의무자 3 + 일련 4.

`lib/livestock/trace-number.ts`가 이 표로 번호를 분해한다. 공공 API 응답에 축종 이름·개체번호 필드가 없을 때 **축종만 보충**한다(`toRecord`, 돼지는 이미 `pigNo`로 판별). 번호에서 추론한 값이라 **원문 `species`나 공용 캐시에 "조회된 사실"처럼 넣지 않는다**. 닭·오리는 카테고리에 "닭/오리" 한 덩어리만 있어 둘 다 그쪽으로 옮기고, 계란은 카테고리가 없어 null.

### 명세서에서 이력번호 구조 활용 (2026-09-24, 사장님 선택 "A")

소를 뺀 축종의 앞자리(돼지 첫 7자리 = 축종+농장, 닭·오리 첫 4자리 = 축종+도축장, 계란 첫 8자리)는 **출처**를 가리킬 뿐 품목·부위·등급이 아니라서, 앞자리만으로 명세서 줄을 골라 상품에 붙이지는 않는다(엉뚱한 상품에 붙을 위험). 대신 **12자리 구조로 명세서를 읽을 때 검증**만 한다:

- `document-parser.ts`: 이력번호 칸 후보가 여럿이면 축종코드까지 맞는 값이 많은 칸을 고른다(12자리 숫자는 코드 열 등에도 흔함).
- `document-requirements.ts` 줄별 진단(막지 않고 짚기만, 권고 수준·`FROM_STAFF`): **`TRACE_CODE_UNKNOWN`** — 12자리인데 첫 자리가 0·1·2·3·5가 아님(번호를 잘못 읽었거나 이력번호가 아닌 값), **`TRACE_SPECIES_MISMATCH`** — 번호의 축종과 품목명의 축종이 다름(품목명에 축종 단어가 **하나만** 명시된 경우만 판단, 부위 이름은 소·돼지가 겹쳐 근거로 안 씀).
- 15자리·L 접두어 묶음번호는 구조 정보가 없어 검사 대상이 아니다. 스캔·바코드 입력은 첫 자리를 제한하지 않는다(공급처 자체 코드·혼합 박스 때문).
- 아직 안 한 것: 앞자리가 같은 줄을 "추천"으로 띄우기(B), 닭·오리를 번호 첫 자리만으로 상품 확정하기(C — 닭/오리 카테고리 분리 결정 후).

## 확인된 조회 사실 / 남은 문제

- 소: 이력조회가 **부위·원산지를 주지 않는다**(`docs/livestock-inbound-tracking.md`, 메모리 trace-api-no-part-name). 돼지 실호출(`140077000150`): 축종 이름 없음, 부위·원산지 없음, 등급 "2등급 이상", 도축일·가공장 3곳·농장주 있음. → 이력만으로는 키의 부위를 못 채운다. 채우는 곳은 **명세서 줄·바코드 상품코드(GTIN)·사장님 지정**.
- 닭·오리: 오리 번호 `521060600101`(코드 5, 도축장 210)은 KAPE 조회가 결과 0건(옵션 1~9 전부). 번호 문제인지 이 API가 가금류를 안 주는지 **미확인** — 앱/mtrace.go.kr에서 같은 번호를 직접 조회해 확인 필요.
- **알려진 문제(미수정):** `fetchTraceRecord`의 "형식 판별 실패 시 순차 폴백"에 `poultry` 종류가 있는데 `master_livestock.trace_kind` CHECK는 `individual/group/imported`만 허용한다 — 그 경로로 캐시하면 저장이 실패한다(현재는 12/15자리·L접두어·영문접두어 밖의 형식일 때만 도달).
- 결정 대기: 닭/오리 카테고리 분리(현재 `product_categories`에 "닭/오리" 한 덩어리, 계란 없음), 가금류를 번호만으로 상품 생성할지(API 결과가 없어도).
